# 第2章　ファイルとフォルダから構造を始める

## この章の目的

何もないApplicationから、まだ決めすぎない最小構造を作り、新しい概念を横へ追加し、一つの概念を縦へ深掘りできる状態へ進む。

## 1. 小さければ一つのModuleで始める

最初の要求がJob登録だけなら、`app.py`一つでよい。

```python
jobs: list[dict] = []


def create_job(name: str) -> dict:
    job = {
        "id": len(jobs) + 1,
        "name": name,
        "status": "created",
    }
    jobs.append(job)
    return job
```

この時点で、Entity、Repository、Controller、DTOを分けても、それぞれの差を説明する材料がない。

フォルダを作らないことは、設計をしないことではない。現在の要求に対して、まだ一つの処理として扱うと判断している。

## 2. 異なる意味が同じ場所に現れたら構造化を始める

Web、Database、権限、状態変更が加わる。

```python
def change_job_status(request):
    user = authenticate(request)
    connection = connect_database()
    row = connection.execute(...).fetchone()

    if not user.can_edit_job(row["id"]):
        raise Forbidden()

    if row["status"] == "completed":
        raise ValueError(...)

    connection.execute(...)
    connection.commit()
    return render_template(...)
```

ここには少なくとも、外部入力、利用目的、Job状態、永続化、Transaction、外部出力がある。

一つの関数で動作することと、一つの意味として扱えることは別である。異なる意味を説明できるようになった時点が、構造化を始める観測点になる。

## 3. 最初の三つの親概念

業務Applicationでは、比較的早い段階で次の違いが現れやすい。

```text
data_component/
feature/
entry/
```

- `data_component/`は、何を保持・参照・変更するか
- `feature/`は、何を達成するか
- `entry/`は、どの外部経路から利用されるか

先ほどの処理なら、次のように置き直す候補が得られる。

```text
data_component/
    job.py
feature/
    change_job_status.py
entry/
    web.py
app.py
```

これは一意の正解ではない。現在説明できる大きな意味へ名前を与えた、最初の配置である。

## 4. 役割より親となる意味を先に置く

Repository、Query、UseCase、Controllerはコードの役割を表す。

Job、Change Job Status、Webは、コードをまとめる親概念になり得る。

例えばRepositoryという理由だけで、最初から次の構造にする必要はない。

```text
repository/
    job_repository.py
```

Jobについての永続化と説明できるなら、Jobの内部が増えた時点で次のように置ける。

```text
data_component/
    job/
        __init__.py
        domain.py
        repository.py
```

親概念と内部役割を分けて考える。

## 5. 横への追加と縦への深掘り

新しい利用目的が増えたら、兄弟として追加できる。

```text
feature/
    create_job.py
    complete_job.py
    reschedule_job.py
```

一つのFeature内部に異なる役割が現れたら、同名Packageへ成長させられる。

```text
feature/
    complete_job/
        __init__.py
        usecase.py
        query.py
```

Data ComponentやEntryも同じように成長できる。

```text
data_component/
    job.py
    schedule.py

entry/
    web.py
    cli.py
```

横と縦のどちらへ進むかは、増えた意味によって判断する。ファイル数だけでは決めない。

## 6. 三つの分類を閉じた型にしない

外部サービス固有の通信、認証、変換、失敗制御が独立した意味を持つなら、次の概念を追加できる。

```text
external_service/
    stripe.py
```

管理機能が一般機能と異なる利用者、権限、変更理由を持つなら、次の構造も候補になる。

```text
feature/
feature_admin/
```

`data_component / feature / entry`はブートストラップであり、すべてのコードを押し込む閉じた分類ではない。

## 7. 名前は配下を検討する手掛かりになる

`entry/web/`と名付けたなら、その配下のコードがWebという入口なしでも同じ意味で成立するかを確認できる。

`data_component/job/`と名付けたなら、その配下のコードをJobという意味で説明できるかを確認できる。

名前は配置を自動決定しない。それでも、親概念と配下の内容がずれていないかを検討する基準にはなる。

### 例

```text
entry/
    web/
        import_job.py
```

最初はWeb Uploadだけで使われていたため、この配置だったとする。後からCLIでも同じImport処理が必要になり、HTTPやUploadから独立した利用目的と分かったなら、次の配置を検討できる。

```text
feature/
    import_job.py
```

利用箇所が二つになったから移すのではない。Webという親概念がなくても同じ意味で成立すると判断したため移す。

## 8. 初期構造が保証しないこと

この構造だけでは、適切なData Component境界もFeature境界も決まらない。

```text
data_component/
    everything.py
```

のような巨大な概念も作れてしまう。反対に、細かすぎるFeatureを大量に作ることもできる。

初期構造が提供するのは、発見した概念を配置し、後から更新できる余地である。概念発見と境界判断は、実装後の俯瞰を含めて行う。

## 9. この章の結論

何も必要なければ一つのModuleで始める。異なる意味を説明できるようになったら、現在分かる大きな概念へ名前を与える。

`data_component / feature / entry`は、コードを読む前の構造上の手掛かりを作り、横への追加と縦への深掘りを受け入れるための初期値である。最終分類でも、境界を自動決定する規則でもない。
