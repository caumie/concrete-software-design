# 第5章　概念の配下・公開面・利用

## この章の目的

コードをどの概念の配下へ置くか、別概念から何を公開するか、公開された概念をどのように利用するかを分けて考える。名前、Module、Package、Protocolの配置を同じ判断へ接続する。

## 1. 配下と利用は別の関係である

次の構造を考える。

```text
data_component/
    job/
        __init__.py
        domain.py
        repository.py

feature/
    complete_job/
        __init__.py
        usecase.py
```

`domain.py`と`repository.py`はJobという概念の配下にある。

`complete_job/usecase.py`はJob Data Componentの公開操作を利用する。

配下に置く関係と、別概念を利用する関係を混同しない。RepositoryがJob配下にあっても、Job Entity自身がRepositoryを呼ぶという意味にはならない。

本書では「所有」という語を使う場合、概念の配下に置く関係に限定する。依存関係は「利用する」「公開操作を呼ぶ」「直接依存として明示する」と表現する。

## 2. 概念は一つのModuleから始められる

新しい概念が一つのファイルで説明できるなら、最初からフォルダを作らない。

```text
data_component/
    job.py

feature/
    complete_job.py
```

内部役割が増えたときに、同名Packageへ成長させる。

```text
data_component/
    job/
        __init__.py
        domain.py
        repository.py
```

概念を作ることと、その概念のためにフォルダを作ることは同じではない。

## 3. 公開面は通常の利用入口を示す

Pythonでは、Package内部を物理的に隠せるとは限らない。

```python
from data_component.job.repository import save
```

と直接importすることもできる。

公開面の目的は、内部参照を不可能にすることではない。別概念から通常どこを入口にするかを示すことである。

```python
# data_component/job/__init__.py

from .domain import Job, JobId
from .service import complete_job

__all__ = ["Job", "JobId", "complete_job"]
```

利用側は次のように書ける。

```python
from data_component.job import complete_job
```

公開面は、概念ごとに持つ。無関係な操作を一つの巨大なApplication Facadeへ集めない。

## 4. 深い参照を観測する

Featureが次のようにJob内部を個別に利用しているとする。

```python
from data_component.job.domain import Job
from data_component.job.repository import get, save
from data_component.job.transition import validate_transition
```

このFeatureはJob内部の再構成に強く依存する。

深いimportを禁止するだけではなく、なぜ必要になったかを見る。

- 公開操作が不足している
- 利用側が内部の処理順序を持ちすぎている
- 内部に置かれたコードが、実は別概念である
- 同じ概念内部なので深い参照に合理性がある

同じPackage内部では、`from .repository import get`のような参照を過剰に迂回させる必要はない。概念内部と概念外部では、必要な安定性が異なる。

## 5. 親概念の意味を越えていないかを見る

配置を見直す問いの一つは次である。

> このコードは、親となる概念がなくても同じ意味で成立するか。

### 例

```text
feature/
    complete_job/
        notification.py
```

この通知がComplete Jobの成功条件に固有なら、Feature配下に置ける。

後からCancel JobやReschedule Jobでも同じ通知契約を利用し、Complete Jobなしでも「Job Notification」として説明できるようになったなら、親概念を見直す材料になる。

利用箇所数だけで移動せず、親概念を越えた意味が成立したかを見る。

## 6. 名前は配下を検討する基準になる

名前はコード内部を説明し切らない。それでも、配下に置かれたコードとのずれを検討する基準になる。

`entry/web/`にCLIでも使う処理が増えた。`data_component/job/`にCustomer管理が入った。`shared/`に異なる業務規則が集まった。

このような状態では、名前、配置、概念境界のいずれかを見直す。

一般的な役割名を使ってもよいが、一般的な意味と異なる定義を必要とするなら、プロジェクトで説明しやすい具体名を検討する。

## 7. InterfaceやProtocolも意味と利用範囲で置く

Interfaceだからトップレベルの`interfaces/`へ置くとは限らない。

一つのModuleだけが必要とする呼び出し契約なら、そのModuleの近くへ置ける。

```python
class SendNotification(Protocol):
    def __call__(self, job_id: int) -> None:
        ...
```

同じPackage内の複数Moduleが同じ契約を利用するなら、Packageの公開面または契約を説明できるModuleへ置ける。

複数の概念が本当に同じ意味の契約を共有するなら、名前を持つ共有概念へ置くこともできる。

利用側ごとに最小のInterfaceを必ず作る規則にはしない。例えばJob Repositoryについて、`get`、`save`、`delete`等を持つ共通契約がプロジェクト内で同じ意味を保つなら、一部の利用側が全操作を使わなくても共通Interfaceとして扱える。

重要なのは、Interfaceの細かさを機械的に決めることではなく、何の契約で、どの範囲が同じ意味を共有するかを説明することである。

## 8. 配置を考える順序

配置を考えるときは、次の問いを使える。

1. このコードは何についてのコードか
2. 現在どの概念の配下なら意味を説明できるか
3. その配下で何という役割を持つか
4. 別概念から直接利用する必要があるか
5. 利用するなら何を公開するか
6. 利用側は内部構造をどこまで知る必要があるか
7. 親概念がなくても同じ意味で成立するか
8. 利用範囲が変わったことで配置を見直す必要があるか

この問いが判断を少なくするとは限らない。判断結果を、配置、公開面、importとして具体的に反映するために使う。

## 9. この章の結論

概念の配下に置くこと、別概念へ公開すること、公開された概念を利用することは別の関係である。

概念は小さなModuleから始め、内部役割が増えたときにPackageへ成長させる。公開面は通常の利用入口を示す。名前、深いimport、Protocolの利用範囲は、概念境界を再検討する材料になる。
