# 第20章　小さなアプリケーションを成長させる

## 1. 何もない状態から始める

最初の要求は、Jobを登録することだけとする。

```text
app.py
```

```python
jobs: list[dict] = []


def create_job(name: str) -> dict:
    job = {
        "id": len(jobs) + 1,
        "name": name,
        "status": "created",
    }

    jobs.append(job)
    return job
```

この時点では分けない。

一つの処理しかなく、概念差を観測する材料も少ないからである。

---

## 2. 一覧表示を追加する

```python
def list_jobs() -> list[dict]:
    return jobs.copy()
```

CreateとListという二つの利用目的が見えた。

しかし、まだ`app.py`で十分に理解できる。

ここでも構造を急がない。

---

## 3. Webを追加する

HTTP RequestとHTML出力が加わる。

```python
def create_job_handler(request):
    name = request.form["name"]
    job = create_job(name)

    return render_template(
        "job.html",
        job=job,
    )
```

ここで、

- Web入力
- Job登録

という異なる変更理由が見える。

まずWeb Entryを切り出す。

```text
entry/
    web.py

app.py
```

まだFeatureを作らなくてもよい。

---

## 4. Databaseを追加する

Job登録がDatabaseを使う。

```python
def create_job(
    name: str,
    connection,
):
    connection.execute(
        """
        INSERT INTO jobs(name, status)
        VALUES (?, ?)
        """,
        (name, "created"),
    )

    connection.commit()
```

ここでも、Create Jobだけなら一つの処理として理解できる。

Repositoryを先に作る必要はない。

---

## 5. 状態変更を追加する

```python
def change_job_status(
    job_id: int,
    status: str,
    connection,
):
    row = connection.execute(
        """
        SELECT id, status
        FROM jobs
        WHERE id = ?
        """,
        (job_id,),
    ).fetchone()

    if row["status"] == "completed":
        raise ValueError(...)

    connection.execute(
        """
        UPDATE jobs
        SET status = ?
        WHERE id = ?
        """,
        (status, job_id),
    )

    connection.commit()
```

Create JobとChange Job Statusという利用目的が並んだ。

ここでFeatureというまとまりを導入する。

```text
feature/
    create_job/
        usecase.py

    change_job_status/
        usecase.py

entry/
    web.py
```

---

## 6. さらに状態操作が増える

Complete Jobを追加する。

```python
def execute(
    job_id: int,
    connection,
):
    row = connection.execute(...).fetchone()

    if row["status"] != "running":
        raise ValueError(...)

    connection.execute(...)
    connection.commit()
```

Cancel Jobも増える。

この時点で、

- 状態を読む
- 状態遷移可能性を判断する
- 状態を変更する

という同じ意味が複数Featureに現れる。

ここでJob Data Componentを導入する。

```text
data_component/
    job/
        domain.py

feature/
    create_job/
    change_job_status/
    complete_job/
    cancel_job/
```

---

## 7. Job Domainを具体化する

```python
class Job:
    def __init__(
        self,
        job_id: int,
        status: str,
    ):
        self.id = job_id
        self.status = status

    def complete(self) -> None:
        if self.status != "running":
            raise ValueError(...)

        self.status = "completed"

    def cancel(self) -> None:
        if self.status == "completed":
            raise ValueError(...)

        self.status = "cancelled"
```

状態遷移規則をFeatureからJobへ移す。

これによってFeatureは処理順序へ戻る。


Repositoryをトップレベルの技術層へ移さず、Jobの近くへ置く。

## 10. Repository依存を局所化する

Job ServiceがRepositoryを直接使う。

```python
@dataclass(frozen=True, slots=True)
class Dependencies:
    repository: JobRepository

    @classmethod
    def default(cls) -> Self:
        return cls(
            repository=repository_default,
        )
```

Feature側へRepository依存を運ばない。

## 11. UseCaseの標準構成を作る

```python
@dataclass(frozen=True, slots=True)
class Dependencies:
    conn: Connection
    complete_job: CompleteJob

    @classmethod
    def default(cls) -> Self:
        return cls(
            conn=connection_factory(),
            complete_job=complete_job_default,
        )
```

```python
def execute(
    job_id: int,
    *,
    dependencies: Dependencies | None = None,
):
    if dependencies is None:
        dependencies = Dependencies.default()

    dependencies.complete_job(
        job_id,
        dependencies.conn,
    )

    dependencies.conn.commit()
```

通常実行では、このUseCaseの近傍にある標準構成を使う。

---

## 12. Scheduleを追加する

Reschedule Jobを実装すると、Job内部にSchedule情報が増える。

当初は、

```text
data_component/
    job/
        schedule.py
```

でもよい。

しかし実装が増え、

- Schedule独自状態
- Schedule独自変更
- Jobとは異なるライフサイクル

が見えたなら、

```text
data_component/
    job/
    schedule/
```

へ分割する。

---

## 13. 一つのUseCaseから両方を使う

```python
@dataclass(frozen=True, slots=True)
class Dependencies:
    conn: Connection
    ensure_reschedulable: EnsureReschedulable
    change_period: ChangePeriod

    @classmethod
    def default(cls) -> Self:
        return cls(
            conn=connection_factory(),
            ensure_reschedulable=ensure_reschedulable_default,
            change_period=change_period_default,
        )
```

```python
def execute(
    command,
    *,
    dependencies: Dependencies | None = None,
):
    if dependencies is None:
        dependencies = Dependencies.default()

    dependencies.ensure_reschedulable(
        command.job_id,
        dependencies.conn,
    )

    dependencies.change_period(
        command.schedule_id,
        command.period,
        dependencies.conn,
    )

    dependencies.conn.commit()
```

Data Componentを分割しても同じTransactionを維持できる。

## 15. 通知を追加する

Complete Jobの仕様として通知が必須なら、UseCase Dependencyへ通知関数を追加できる。


## 19. 既存構造から意味を取り出す

実際のApplicationでは、現在の構造と、後から見えた意味の境界が一致していないことがある。

実際には、

```text
domain/
service/
repository/
infrastructure/
utils/
shared/
web/
```

のような役割別構造へ先に進み、一つの変更が複数フォルダへ散ることも多い。

この状態から、現在変更する意味を手掛かりにFeature、Data Component、Entryを取り出せる。既存コード・Test・依存関係・公開APIが現在の構造を利用しているため、移行も設計対象になる。

---

## 20. 段階的に移行する

既存構造から、現在変更する意味の単位で段階的に移行できる。

例えばComplete Jobを変更する機会に、

```text
feature/
    complete_job/
        usecase.py
```

を作り、旧`JobService.complete()`から責任を移す。

さらにJobの状態遷移規則を、

```text
data_component/
    job/
        domain.py
```

へ移す。

Repositoryも必要なら、

```text
data_component/
    job/
        repository.py
```

へ近づける。

移行期間中は、

```text
service/
repository/
feature/
data_component/
```

という新旧構造が共存する。

依存方向も一時的に複雑になる。

同じ概念が旧構造と新構造に二重化することもある。

移行単位、互換用公開面、二重化を解消する終了条件までを一緒に決める。

---

## 21. 現在変更する範囲から移行する

具象設計論では、

> 現在変更する具体的な意味から境界を見直す

という方法を取れる。

ただし、この方法は移行コストを消すものではない。

- 旧構造との接続
- 一時的なAdapter
- Testの移行
- import pathの変更
- 新旧公開面の共存

を扱う必要がある。

初期構造では、後から分割・統合できることに加え、その時点で説明できる意味を明示する。これにより、移行時にもどの意味を取り出すかを判断しやすくなる。

---

## 22. 移行時に意味を再評価する

### 名前と責任を一緒に変える

`service/`を`feature/`へRenameするだけでは、責任は変わらない。

### 旧構造を意味単位へ組み直す

旧ServiceをFeatureへ、旧RepositoryをData Componentへ機械的に移すだけでは、概念の再評価にならない。

### Sharedの共有範囲を確認する

Sharedを広い依存先として維持する判断もできる。異なる意味が混在しているなら分割し、意図した共有なら公開面と依存範囲を維持する。

### 必要な抽象だけを追加する

Port、Event、Factory、Interfaceを一式追加すると、移行そのものの複雑性と抽象化の複雑性が重なる。
