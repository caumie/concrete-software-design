# 第11章　よく使う設計用語

## この章の目的

日常的なApplication設計で現れやすい既存語彙を、具体的なコード配置と利用方法へ接続する。

本章は、DDD、Clean Architecture、Hexagonal Architectureなどを個別に要約するものではない。また、既存用語を新しいフォルダ分類として追加するものでもない。本書の実装で繰り返し現れる用語について、何を区別するための概念か、この設計論ではどのように解釈するか、どこへ配置するか、どのような利点と代償があり、いつ不要なのかを示す。

個別の用語は、すでに役割が現れた時点の断面として扱う。小さな`app.py`から各構造へ至るまでの過程は、Applicationの成長を扱う章で説明する。

## 1. 用語より先に、親となる意味を置く

Entity、Repository、UseCase、DTO、Port、Adapterは、コードの性質や役割を表す。しかし、その名前だけでは親となる概念までは決まらない。

例えばRepositoryという役割が分かっても、次のどこへ置くかは別の判断である。

```text
repository/
    job_repository.py
```

```text
data_component/
    job/
        repository.py
```

```text
feature/
    import_job/
        repository.py
```

Jobの状態を復元し保存するなら、Job Data Componentの配下で説明しやすい。Import Jobの処理途中にしか存在しないデータを保存するなら、Import Job Featureの配下が候補になる。Repositoryという役割だけを理由に、すべてのRepositoryを一か所へ集める必要はない。

具象設計論では、既存語彙を次の順序で適用する。

1. その用語が何を区別するためのものかを確認する
2. 現在のコードのどこに、その役割が実在するかを確認する
3. そのコードが何についてのものかを、親となる概念で説明する
4. 親概念の配下で、役割名をModule名や型名として使う
5. 公開面、直接依存、Transaction、Testへの影響を確認する
6. 得られる利点と、追加される型、変換、間接参照の代償を比較する

この順序なら、`repository.py`や`adapter.py`は既存の構成を模倣するためのファイルではなく、親概念の内部に実在する役割を表すファイルになる。

## 2. 一つのコードに複数の用語が成立する

既存語彙は、互いに排他的な分類ではない。

- SQLからJobを復元するコードは、Repositoryであると同時に永続化Adapterでもある
- HTTP RequestをUseCaseの入力へ変換するHandlerは、Controllerであると同時にInbound Adapterでもある
- 一覧表示用の`JobListItem`は、Read Modelであると同時にDTOでもある
- UseCaseが必要とする`SendNotification`はPortであり、Pythonでは`Protocol`として表現できる

同じコードへ複数の説明が成立しても、用語ごとにファイルを分ける必要はない。Repositoryと永続化Adapterの二つの役割を持つ実装に対し、`repository.py`と`persistence_adapter.py`を二重に作ることは避ける。親となる意味を決め、その場所で役割を最も説明しやすい名前を選ぶ。

本書の基本構造とも一対一には対応しない。

| 既存語彙 | 主に区別するもの | 配置を考える起点 |
| --- | --- | --- |
| Entity・Value Object・Aggregate | 同一性、値、整合性の単位 | 状態を持つData Component |
| Domain Service | 一つのObjectに属さないDomain上の判断 | その判断が属するData Component |
| UseCase・Application Service | 利用目的と完了までの協調 | Feature、またはEntry固有の目的 |
| Repository | 意味ある対象の取得と保存 | 対象となるデータ概念 |
| Query・Read Model | 読み取り目的と必要な形 | その情報を必要とするFeatureやEntry |
| DTO | 境界を越えて運ぶデータ契約 | その契約を定義する側 |
| Port・Interface・Protocol | 利用側が必要とする能力の契約 | その能力を直接利用するModule |
| Adapter | 異なる表現や技術の変換 | 境界の意味、または外部サービス |
| Controller・Presenter | Inbound入力と外部向け出力表現 | Entry |
| Unit of Work | 変更追跡とTransaction操作 | Featureの成功範囲とResource実装 |
| Event | 起きた事実と、そのConsumer | 事実を定義する概念と利用する概念 |

この表は配置の対応表ではない。検討を始める場所を示すものである。

## 3. Entity、Value Object、Aggregateを状態の意味として使う

### 概念と解釈

Entityは、属性が変化しても同じ対象として追跡されるものを表す。同一性とライフサイクルが中心になる。

Value Objectは、識別子ではなく値そのものによって等しさが決まるものを表す。値の組合せに成立条件がある場合、その条件を値と同じ場所へ置ける。

Aggregateは、同じ整合性規則の下で変更されるEntityとValue Objectのまとまりである。外部からの変更入口となるAggregate Rootを定め、内部状態を無制限に直接変更させない。

Data Componentはコード配置上の親概念であり、Aggregateと同義ではない。一つのData Componentが一つのAggregateを含むことも、複数のAggregateやRead Modelを含むこともある。

### 配置例

```text
data_component/
    job/
        __init__.py
        domain.py
        repository.py

    schedule/
        period.py
```

```python
# data_component/job/domain.py

@dataclass
class Job:
    id: JobId
    status: JobStatus

    def complete(self) -> None:
        if self.status is not JobStatus.RUNNING:
            raise InvalidJobTransition()
        self.status = JobStatus.COMPLETED
```

```python
# data_component/schedule/period.py

@dataclass(frozen=True, slots=True)
class Period:
    start: date
    end: date

    def __post_init__(self) -> None:
        if self.end < self.start:
            raise ValueError("end must not precede start")
```

`Job`は同一性と状態遷移を持つためEntityとして説明できる。JobがRevisionやAssignmentを内部に持ち、それらをJobの操作を通して一緒に整合させるなら、JobをAggregate Rootとして扱う理由が生まれる。`Period`は開始日と終了日の組を一つの値として扱うためValue Objectとして説明できる。

### 判断理由、利点、不要な場合

Entityへ状態遷移を置くと、どのFeatureからJobを変更しても守る規則をJobの近くへ集められる。Value Objectへ成立条件を置くと、不正な値の組合せを複数の利用側で繰り返し検証せずに済む。Aggregateは、複数の状態を同時に見なければ守れない規則と、外部へ公開する変更入口を示せる。

その代わり、Objectへの変換、永続化とのMapping、型の数が増える。Aggregateを大きくしすぎれば、取得、競合、変更の範囲も広がる。Aggregateは内部の整合性と変更入口を示すが、Featureが扱うDatabase Transactionと必ず一対一にはならない。一つのUseCaseが複数Aggregateの公開操作を同じTransactionで利用しても、それだけで一つのAggregateになるわけではない。

一覧表示の一行、外部APIのResponse、処理途中で一度だけ使う値までEntityにする必要はない。`int`を包むだけで誤用防止、検証、振る舞い、型上の区別のいずれも得られないなら、Value Objectは不要である。Data Componentのフォルダを作ったことだけを理由に、その中身をAggregateと呼ぶ必要もない。

## 4. Domain ServiceとApplication Serviceを分ける

### 概念と解釈

`Service`は意味の広い語である。少なくとも、Domain ServiceとApplication Serviceでは判断主体が異なる。

- Domain Serviceは、Domain上の規則だが、一つのEntityやValue Objectだけには自然に置けない判断を表す
- Application Serviceは、利用目的を完了するために複数の能力を順序づけ、Transactionや外部連携を協調させる

本書のUseCaseは、Application Serviceに近い役割を持つ。ただし、Featureという親概念とApplication Serviceという役割は同義ではない。

### 配置例

```text
data_component/
    schedule/
        allocation_policy.py

feature/
    reschedule_job.py
```

複数のScheduleと担当者の稼働条件から割当可否を判断する純粋な規則なら、`allocation_policy.py`をDomain Serviceとして説明できる。

Jobの再予定可否を確認し、Scheduleを変更し、履歴を記録してcommitする処理は、`feature/reschedule_job.py`のUseCaseであり、Application Serviceとして説明できる。

### 判断理由、利点、不要な場合

Domain Serviceを使うと、特定のEntityへ無理に責任を寄せず、Domain上の判断へ名前を与えられる。Application Serviceを使うと、利用目的の成功条件と処理順序を、個々のDomain ObjectやEntryから分けられる。

ただし、`service.py`や`services/`という名前だけでは、何についてのServiceか、どちらのServiceかが分からない。親Packageが十分に意味を示すなら`data_component/job/service.py`でも成立するが、役割が複数になれば`allocation_policy.py`や`complete_job.py`のような具体名を使う。

本書の`data_component/job/service.py`は、Jobを取得し、状態規則を適用し、保存する公開操作である。ファイル名だけを理由にDomain Serviceとみなすものではない。EntityのMethodで自然に表せる規則をDomain Serviceへ移す必要も、数行のUseCaseをClass化する必要もない。

## 5. Repositoryを対象概念の取得・保存として使う

### 概念と解釈

Repositoryは、Database Table一般を操作する層ではなく、Applicationが意味ある対象を取得・保存するための契約である。Domain Modelを使う場合は、保存形式から対象を復元し、変更結果を保存形式へ戻す役割を持つ。

### 配置例

```text
data_component/
    job/
        domain.py
        repository.py
        service.py
```

```python
# data_component/job/repository.py

class DefaultJobRepository:
    def get(self, connection: Connection, job_id: JobId) -> Job:
        row = connection.execute(...).fetchone()
        return Job(...)

    def save(self, connection: Connection, job: Job) -> None:
        connection.execute(...)
```

Repositoryを直接利用するのが`service.py`だけなら、利用側が必要とする契約を`service.py`へ置ける。

```python
# data_component/job/service.py

class JobRepository(Protocol):
    def get(self, connection: Connection, job_id: JobId) -> Job:
        ...

    def save(self, connection: Connection, job: Job) -> None:
        ...
```

通常利用する`DefaultJobRepository`は、`service.py`に置くModule localな`Dependencies.default()`で選べる。外側のCompositionから同じ`Dependencies`を明示的に渡す形も取れる。いずれの場合も、FeatureがJobの取得・保存手順を組み立てる必要がなければ、Jobの公開操作だけを利用する。Poolや長寿命Resourceのlifecycleは、Repositoryの配置とは別に第12章と第14章で扱う。

Featureは、Jobの取得、変更、保存手順を自ら組み立てる必要がなければ、RepositoryではなくJobの公開操作を利用する。

```python
from data_component.job import complete_job
```

複数のJob内部Moduleが同じRepository契約を共有するなら、契約と標準実装を`repository.py`へまとめる選択もできる。Interfaceは必ず利用側のファイル、実装は必ず遠くのInfrastructureフォルダ、という配置規則にはしない。利用範囲、公開面、変更理由を具体的に見る。

### 判断理由、利点、不要な場合

Repositoryを置くと、保存形式、SQL、ORMの操作をJobの利用側から分けられる。Domain Modelの復元と保存を一か所で扱え、Jobの公開操作をRepositoryのFakeでModule Testできる。

代償として、Domain Modelと保存形式のMapping、Repository契約、実装の追跡が増える。ORMのAPIを名前だけ変えて転送するRepositoryは、費用だけを増やすことがある。

Repository実装は永続化Adapterでもある。同じ実装に対して`repository.py`と`adapter.py`を二重に作らない。一覧表示用のSQL、集計Query、外部APIの検索結果までRepository経由にする必要もない。

## 6. QueryとRead Modelを利用目的へ置く

### 概念と解釈

Queryは、状態を変更せず、必要な情報を読み取る役割である。Read Modelは、その読み取り目的に合わせた結果の形である。

QueryはRepositoryの読み取りMethodと同義ではない。Repositoryが対象の復元を目的とするのに対し、Queryは画面、帳票、判定、外部出力などが必要とする形を直接返せる。

### 配置例

Complete Jobの確認画面だけに必要な情報なら、Featureの配下へ置ける。

```text
feature/
    complete_job/
        usecase.py
        query.py
```

一覧を閲覧すること自体が利用目的なら、読み取りだけのFeatureにできる。

```text
feature/
    list_jobs.py
```

```python
@dataclass(frozen=True, slots=True)
class JobListItem:
    job_id: int
    name: str
    status: str


def execute(condition: JobListCondition, connection: Connection) -> list[JobListItem]:
    rows = connection.execute(...)
    return [JobListItem(...) for row in rows]
```

WebのSessionや表示状態がなければ意味を持たないQueryなら、`entry/web/`の配下も候補になる。Queryという役割だけを理由にトップレベルの`query/`を作らない。

### 判断理由、利点、不要な場合

読み取り目的に必要な列と結合を直接表せるため、更新用のDomain Modelを不完全な形で復元せずに済む。画面や帳票の変更理由を、状態変更の規則から分けられる。

その代わり、似たRead ModelやSQLが複数現れることがある。同じTableを読むことではなく、同じ読み取り概念として一緒に変わるかを見て共通化する。既存の公開操作が返す値をそのまま利用できるなら、専用Queryは不要である。

## 7. DTOを境界の契約として配置する

### 概念と解釈

DTOは、ある境界を越えてデータを運ぶための形である。Domain上の状態遷移や業務判断を持たず、送り手と受け手の間で必要なデータを明示する。

DTOをどちら側が持つかは、データの流れる向きだけでは決まらない。そのDTOが、どの契約の意味を表しているかで決める。

### 配置例

```text
entry/
    web/
        complete_job.py

feature/
    complete_job/
        usecase.py

external_service/
    mail/
        adapter.py
```

- `CompleteJobRequest`がHTTP Request bodyを表すなら、Web Entryが持つ
- `CompleteJobCommand`がFeatureの入力契約を表すなら、Complete Job Featureが持つ
- `CompleteJobResult`がFeatureの公開結果を表すなら、Complete Job Featureが持つ
- Mail provider固有のRequest・Response型は、Mail Adapter内部に閉じ込める

```python
# feature/complete_job/usecase.py

@dataclass(frozen=True, slots=True)
class CompleteJobCommand:
    actor_id: int
    job_id: int
    reason: str


@dataclass(frozen=True, slots=True)
class CompleteJobResult:
    job_id: int
    completed_at: datetime
```

EntryはHTTPから得た値を`CompleteJobCommand`へ変換する。必要ならFeatureの結果をEntryがHTTP Response表現へ変換する。

### 判断理由、利点、不要な場合

DTOを置くと、外部表現やFramework型の変更範囲を境界へ留められる。Featureが受け取る入力と返す結果を、公開契約として示せる。外部APIの項目名や欠損表現を内部へ広げずに済む。

代償は、似た型と変換処理が増えることである。境界ごとに機械的にDTOを複製すると、意味の差がない型を追跡し続けることになる。RequestとCommandの項目が同じであっても、Framework依存、入力の意味、Validation、変更理由が異なるなら分ける理由がある。これらの差がなく、標準型をそのまま渡せば契約を十分に表せるなら、専用DTOは不要である。

`dto.py`は、親Packageが何のDTOかを十分に示す場合には使える。複数の入力、結果、外部契約が混在するなら、`command.py`、`result.py`、具体的なRequest名などで区別する。

## 8. Port・Interface・Protocolを利用側の能力として置く

### 概念と解釈

Portは、Applicationまたは一つのModuleが外部へ要求する能力、あるいは外部へ公開する入口の契約である。Interfaceは契約を表す一般的な手段であり、Pythonの`Protocol`はその一つの表現である。

Port、Interface、Protocolは同義ではない。PortはArchitecture上の役割を表し、Protocolは言語上の型表現を提供する。

### 配置例

Complete Job UseCaseが完了通知の能力を必要とするなら、その呼び出し契約を利用側へ置ける。

```python
# feature/complete_job/usecase.py

class SendCompletionNotice(Protocol):
    def __call__(
        self,
        job_id: int,
        completed_at: datetime,
    ) -> None:
        ...
```

Job ServiceだけがRepositoryを利用するなら、`JobRepository` Protocolを`data_component/job/service.py`へ置ける。複数Moduleが同じ意味の契約を共有するなら、その共通の親概念へ置く。

Interfaceという役割だけを理由に、トップレベルの`ports/`、`interfaces/`、`protocols/`を作らない。

### 判断理由、利点、不要な場合

利用側が必要とする呼び出し方を示し、外部SDKや具体的な保存技術への直接依存を避けられる。同じ契約でFakeを渡せるため、利用側のModule Testを直接依存の境界で行える。

一方、Interfaceを増やすと実装との対応、命名、変換が増える。一つの共通Interfaceを利用側ごとに細分化することにも、巨大なInterfaceを共有することにも代償がある。何の契約が同じ意味を保つかで範囲を決める。

普通の関数やObjectを引数で受け取れば十分なら、名前付きProtocolは不要である。Dependency Injectionは専用InterfaceやContainerがなくても成立する。

## 9. Adapterを境界の変換として置く

### 概念と解釈

Adapterは、ある側の契約や表現を、別の側が利用できる形へ変換する。HTTP、CLI、Database、外部SDK、Message brokerなどとApplicationの間に現れる。

Adapterは「外部技術を使うコード」の総称ではない。入力、出力、Error、型、呼び出し規約の違いを引き受けるときに、その役割が具体化する。

### 配置例

HTTP RequestをComplete Job Featureへ接続するHandlerは、Controllerであると同時にInbound Adapterとして説明できる。

```text
entry/
    web/
        complete_job.py
```

Request解釈、UseCase呼び出し、Response変換が一つの短いHandlerで読めるなら、ControllerやPresenterを別Classへ分ける必要はない。それぞれが独立して複雑なら、`entry/web/complete_job/controller.py`と`presenter.py`のように、親概念を保ったまま内部役割を分けられる。

Mail providerのSDKを`SendCompletionNotice` Portへ合わせるコードはOutbound Adapterである。Mail接続がComplete Jobだけに固有なら、次の配置が成立する。

```text
feature/
    complete_job/
        usecase.py
        mail_adapter.py
```

認証、Request変換、Timeout、Retry、Rate Limit、Provider固有Errorの変換が、Mail接続として独立した責任を持つなら、次の配置が成立する。

```text
external_service/
    mail/
        __init__.py
        adapter.py
```

`adapter.py`という名前は、`external_service/mail/`という親概念が何のAdapterかを示しているため成立する。トップレベルの`adapters/`へ、Mail、Database、HTTPのAdapterを役割だけで集める必要はない。

```python
# external_service/mail/adapter.py

@dataclass(frozen=True, slots=True)
class MailAdapter:
    client: ProviderClient

    def __call__(self, job_id: int, completed_at: datetime) -> None:
        try:
            self.client.send(
                template="job_completed",
                variables={
                    "job_id": job_id,
                    "completed_at": completed_at.isoformat(),
                },
            )
        except ProviderTimeout as error:
            raise MailTemporarilyUnavailable() from error
```

### 判断理由、利点、不要な場合

Adapterへ変換を集めると、外部の型、項目名、Error、SDKの呼び出し方がFeatureやData Componentへ広がるのを防げる。Portと組み合わせれば、利用側の契約を保ったまま外部実装を変更できる。

ただし、Adapterは外部I/Oの物理的な性質を消さない。Mail送信とDatabase commitは、Adapterで包んでも一つのACID Transactionにはならない。Timeout、Retry、重複、部分失敗をどこで扱うかは別に設計する。

一つのFeatureが外部Libraryの純粋な計算関数を一度呼び、その型もErrorも内部の意味と一致しているなら、専用Adapterは不要なことがある。単に関数名を変えて転送するだけのAdapterは追跡経路だけを増やす。

## 10. Unit of WorkとEventを必要な責任だけに使う

Unit of Workは、一連の変更を追跡し、RepositoryとTransaction操作を一つの実行単位として扱うPatternである。Eventは、すでに起きた事実を表し、その事実を別の処理へ公開する。

どちらも、採用するArchitectureの用語を揃えるために必須となる部品ではない。

### Unit of Work

本書では、どこまでを一緒に成功・失敗させるかをFeatureのUseCaseが決める。一つのConnectionを受け取り最後にcommitするだけなら、その責任は次の形で表せる。

```python
def execute(command, connection: Connection) -> None:
    ensure_reschedulable(command.job_id, connection)
    change_period(command.schedule_id, command.period, connection)
    connection.commit()
```

複数の永続化技術、Resource lifecycle、変更追跡を一つの契約として扱う必要があるなら、Unit of Workを導入できる。UseCaseが必要とする契約をFeature近傍に置き、標準実装をDatabase Resourceの意味を持つ場所へ置く。

```text
feature/
    reschedule_job.py       # Unit of Workの利用契約

database/
    unit_of_work.py         # 標準実装
```

トップレベルの`database/`は、Database Resourceの生成・破棄やTransaction実装が、個別Data Componentを越えた独立の意味を持つ場合に置く。

Unit of WorkへすべてのRepositoryを公開すると、FeatureがData Component内部のRepositoryを直接組み合わせる構造になり得る。本書のようにFeatureがData Componentの公開操作を利用する場合、ConnectionやContext Managerで十分なら、別のUnit of Work型は作らない。

### Event

Job CompletedがJobの状態変化として意味を持つなら、`data_component/job/events.py`にDomain Eventとして事実を置ける。その事実を通知目的で利用するHandlerは、`feature/notification/job_completed_handler.py`へ置ける。Event busとの変換は、必要なら`external_service/event_bus/adapter.py`へ置く。

別Applicationへ公開するschema、version、個人情報の除外が独立して変わるなら、外部契約としてIntegration Eventを定義し、Domain Eventから変換する。同じ事実を表していても、内部の事実表現をそのまま外部契約にする必要はない。

Eventを使うと、通知、集計、Audit、外部連携などが、Producerの処理列へすべて直接書かれずに済む。その代わり、Handler登録、配送、失敗、Retry、重複、順序、schema version、監視が増える。Database更新とEvent発行のAtomic性が必要なら、Outbox等も必要になる。

Complete Jobの成功条件として一つの処理をその場で必ず呼ぶだけなら、UseCaseから直接利用する方が処理順序と失敗を追いやすい。依存を見えなくするためだけにEventへ置き換えない。

## 11. 一つの断面に用語を重ねる

ここまでの語彙を、Job完了機能の一つの断面へ重ねる。

```text
data_component/
    job/
        __init__.py
        domain.py
        repository.py
        service.py

feature/
    complete_job/
        __init__.py
        usecase.py
        query.py

entry/
    web/
        complete_job.py

external_service/
    mail/
        __init__.py
        adapter.py
```

| ファイル | 成立する既存語彙 | 親となる意味と配置理由 |
| --- | --- | --- |
| `data_component/job/domain.py` | Entity、Value Object、必要ならAggregate Root | Jobの同一性、状態、規則を扱う |
| `data_component/job/service.py` | Jobの公開操作、Repository Portの利用側 | Jobを取得し、規則を適用し、保存する |
| `data_component/job/repository.py` | Repository、Persistence Adapter | Jobと保存形式を相互に変換する |
| `feature/complete_job/usecase.py` | UseCase、Application Service、Command・Result DTO、必要なPort | Job完了という利用目的と成功までの処理を扱う |
| `feature/complete_job/query.py` | Query、Read Model | Job完了画面が必要とする情報を読む |
| `entry/web/complete_job.py` | Controller、Inbound Adapter、HTTP DTO | HTTPとComplete Job Featureを接続する |
| `external_service/mail/adapter.py` | Outbound Adapter | Mail providerを通知Portへ合わせる |

この構造は、DDD、Clean Architecture、Hexagonal Architectureの用語を一つずつフォルダへしたものではない。Job、Complete Job、Web、Mailという親概念を置き、その内部で実在する役割へ既存の名前を使った結果である。

各用語を適用したことで、次のことを説明できる。

- Jobの同一性と状態規則は、どこで守られるか
- Jobの取得・保存形式は、どこへ閉じ込められるか
- Complete Jobの完了条件と処理順序は、どこで決まるか
- HTTPやMail providerの表現は、どこで内部の契約へ変換されるか
- どのModuleが、どの能力を直接利用するか
- Testでは、どの直接依存を差し替えるか

説明できない役割名が残るなら、既存語彙を置いたこと自体を設計根拠にはしない。例えば`service.py`の内容をDomain Service、Application Service、Data Componentの公開操作のいずれとしても説明できないなら、コードの責任か名前を見直す。

## 12. 既存語彙を採用する基準

既存語彙を使う前に、次を確認する。

1. 一般に使われる意味と、現在のコードの役割が一致しているか
2. その名前によって、同一性、境界、依存、変換、成功範囲のどれかが区別しやすくなるか
3. その用語が含意する規則を、実装と公開面で維持するか
4. 具体的な業務名や操作名より、その役割名の方が説明に適しているか
5. 用語を置くことで増える型、変換、間接参照に見合う利点があるか

一般的な意味と一致するなら、既存語彙は長い説明を短くできる。Repositoryと呼ぶことで、単なるSQL Helperではなく、対象の取得・保存を扱う契約だと共有できる。Adapterと呼ぶことで、外部表現との差を引き受ける役割だと共有できる。

一般的な意味と一致しないなら、独自定義を加えてまで有名な語を使うより、`complete_job`、`allocation_policy`、`mail_client`のような具体名を使う方がよい。

用語を使わないことと、設計上の区別を無視することも同じではない。専用の`Controller` ClassがなくてもEntryのHandlerは入力変換の責任を持てる。`UnitOfWork`型がなくてもUseCaseはTransaction境界を明示できる。役割が存在することと、専用の型やファイルを作ることは別に判断する。

## 13. この章の結論

既存の設計語彙は、コードの役割と設計上の区別を説明するために使う。用語を先にフォルダへせず、現在のコードに役割が現れていることを確認し、そのコードが何についてのものかという親概念の配下へ置く。

Entity、Repository、UseCase、DTO、Port、Adapterなどは、`data_component / feature / entry`と一対一に対応しない。一つのコードに複数の用語が成立することもある。重要なのは用語ごとに構造を増やすことではなく、その用語によって何を分け、どの利点を得て、どの代償を受け入れるかを具体的に説明することである。

このように既存語彙を使えば、抽象的な原則と実装上の配置を接続できる。同時に、用語がまだ不要な場所へ構造を先回りして作ることも避けられる。
