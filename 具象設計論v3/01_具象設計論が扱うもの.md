# 第1章　具象設計論が扱うもの

## この章の目的

具象設計論が何を設計対象とし、何を保証せず、どのような順序で原則をコード配置へ接続するかを定める。

## 1. 抽象原則の後に残る判断を扱う

責任を分ける。依存を明示する。変更理由を揃える。外部境界を分離する。

これらの原則に同意しても、実装時の判断は残る。

- 一つの処理をどのModuleへ置くか
- `feature/complete_job.py`として始めるか、既存Featureへ加えるか
- Repositoryをトップレベルへ置くか、対象概念の配下へ置くか
- Queryを画面、Feature、Data Componentのどこへ置くか
- 依存を普通の引数、型、Factoryのどれで表すか

具象設計論は、この原則とコード配置の間を設計対象にする。

## 2. 構造はコードを読む前の理解補助になる

現在の概念理解を、例えば次の構造へ反映する。

```text
data_component/
    job/
feature/
    complete_job/
entry/
    web/
```

この構造だけでは、コード内部の条件や状態変化までは分からない。それでも、Jobについて調べる起点、Complete Jobという利用目的の存在、Webが入口として区別されていることを検討する手掛かりにはなる。

本書は、このようにファイル・フォルダ構造を、コード内部を読む前に得られる設計情報として扱う。

## 3. 構造は成長と更新を受け入れる

概念は、最初から完全には分からない。

一つのFeatureを実装して初めて、別のFeatureにも現れる状態規則が見えることがある。Jobの一部だと思っていたScheduleが、独立した状態とライフサイクルを持つと分かることもある。

そのため構造には、二方向の更新余地を持たせる。

```text
feature/
    create_job.py
    complete_job.py
```

のように兄弟概念を横へ追加できる。

```text
feature/
    complete_job/
        __init__.py
        usecase.py
        preview.py
```

のように、一つの概念を縦へ深掘りできる。

さらに、既存概念の分割、統合、移動、名前変更を通常の設計活動として扱う。

## 4. 判断結果を構造へ反映する

構造は判断を代行しない。何が一つの概念か、どこまでを公開するか、何を共有するかについて、多くの判断が残る。

具象設計論が求めるのは、その判断を抽象的な説明だけに残さないことである。

例えば、ScheduleをJobから分けたなら、判断結果を次の配置として反映する。

```text
data_component/
    job/
    schedule/
```

後から両者が常に同じ状態とライフサイクルで変わると分かれば、再び統合を検討できる。構造は最終解ではなく、その時点の概念理解を具体的に置いたものになる。

## 5. 具体化・観測・更新を繰り返す

設計活動は次の循環になる。

```text
現在の理解を具体化する
        ↓
コードと利用例を増やす
        ↓
状態・変更理由・依存を観測する
        ↓
概念と配置を再評価する
        ↓
構造を更新する
```

具体化は、実装を急いで設計を省略することではない。事前には得られなかった判断材料を作ることである。

同時に、実装しただけで概念が発見されるわけでもない。増えた具体例を並べ、俯瞰する工程が必要になる。

## 6. 配置までの導出を省略しない

本書の事例では、次の順序を示す。

1. 要求または観測した事実
2. 現在の処理と状態
3. 概念候補と配置候補
4. 候補間の差
5. 暫定的に選ぶ配置
6. 公開面、直接依存、Transaction、Testへの影響
7. 再検討する条件

配置は原則から一意に演繹されるとは限らない。だからこそ、結論だけでなく判断の途中を残す。

### 例

複数FeatureにJobの状態遷移規則が現れたとする。

- 観測: 同じJob状態を読み、同じ遷移条件を使っている
- 候補A: 各Featureへ規則を残す
- 候補B: `shared/job_rules.py`へ置く
- 候補C: `data_component/job.py`を作る
- 選択: Jobの状態と同一性を中心に説明できるため、候補Cを暫定採用する
- 影響: FeatureはJobの公開操作を利用し、状態遷移の詳細を持たない
- 再検討条件: Job配下に異なるライフサイクルの状態が増える

コード例だけを提示するより、この過程を示す方が、別のApplicationへ判断を移しやすい。

## 7. 扱わないこと

具象設計論は、次を保証しない。

- ファイル・フォルダを見るだけで全員が同じように理解できること
- 適切なDomainを自動的に発見できること
- 設計判断が少数になること
- `data_component / feature / entry`だけで適切な境界が決まること
- Pythonの実装例が他言語でも最善であること

Domain理解は、利用者への聞き取り、業務分析、規程、既存システム、運用経験などから得る。具象設計論は、その理解をどの構造へ置き、更新するかを扱う。

## 8. この章の結論

具象設計論の中心は、現在の概念理解を具体的な構造として置き、実装で増えた事実によって更新することにある。

構造は理解を保証しないが、コードを読む前の手掛かりになる。構造は完成形を固定せず、成長と再編を受け入れる。そして、行った設計判断を配置として残し、後から再評価できるようにする。
