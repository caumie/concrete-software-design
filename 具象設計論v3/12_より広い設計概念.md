# 第12章　より広い設計概念

## この章の目的

Application、Domain、Model、実行Processまでを扱う設計概念を、本書の具体的な構造へ接続する。

第11章はEntity、Repository、UseCase、DTO、Port、Adapterなど、個々の実装で遭遇しやすい役割を扱った。本章は、Layer、Composition Root、CQRS、Bounded Context、Context Map、Workflowなど、複数のModuleやApplication全体へ及ぶ概念を扱う。

これらは、用語と同名のフォルダを一つ作れば具体化できるものではない。Bounded ContextはPackageとして表現できる場合も、Application、Repository、Serviceとして表現する場合もある。Ubiquitous Languageは一つのファイルへ置くものではない。Composition Rootは名前より、実装選択、Resource生成、lifecycle、受け渡しを追跡できるかが重要になる。

本章も`app.py`からの成長順序は扱わない。役割がすでに観測された時点の断面として、概念、配置、利点、代償、不要な場合を示す。

## 1. 用語が扱う尺度を先に確認する

設計語彙には、それぞれが扱いやすい尺度がある。

| 尺度 | 主な問い | 代表的な語彙 | 具体化されるもの |
| --- | --- | --- | --- |
| 値・Object | 何を同じものとして扱うか | Entity、Value Object、Aggregate | 型、状態、Method、整合性規則 |
| Module内部の役割 | このコードは何をしているか | Policy、Factory、Mapper、Gateway | 関数、Class、Module、直接依存 |
| 利用目的と境界 | 誰が何を達成し、何と接続するか | UseCase、Port、Adapter、DTO、Query | Feature、公開契約、変換、Test境界 |
| Application構造 | 依存、生成、責任をどう組み立てるか | Layer、Composition Root、DI、CQRS | Package、import、Object graph、Read・Write構造 |
| DomainとModelの境界 | どこで言葉とModelの意味が変わるか | Subdomain、Bounded Context、Ubiquitous Language、Context Map | Namespace、公開面、翻訳、所有、契約 |
| 時間をまたぐ処理 | 複数の成功・失敗をどう進めるか | Workflow、Process Manager、Saga | 状態機械、Event、補償、永続化された進行状態 |
| 実行・運用 | 何を独立して配備・停止・拡張するか | Process、Deployment Unit、Service | Process、Network境界、Database、運用責任 |

用語の尺度と物理構造の大きさは、一対一ではない。Bounded Contextを一つのPackageで表現できる場合も、一つのApplicationや複数Serviceで表現する場合もある。反対に、一つの`policy.py`を作っても、そのPolicyが独立したDomain概念になったとは限らない。

配置を考える前に、次を確認する。

1. その用語は、コードの役割、Modelの境界、実行上の境界のどれを表すか
2. 区別したい事実は、現在の実装と運用に存在するか
3. その区別は、名前だけで足りるか、公開面や依存制約まで必要か
4. どの程度の強さで境界を維持する必要があるか

大きな用語ほど大きなフォルダを作る、という関係ではない。観測した差に対して、必要な強さの構造を選ぶ。

## 2. Domain、Domain Model、Domain Logicを配置名から分ける

### 概念と解釈

Domainは、Applicationが扱う活動、知識、問題の領域である。

Domain Modelは、そのDomainのすべてを写したものではない。特定の目的と境界の中で必要な概念、関係、規則を選んで表現したものである。

Domain Logicは、そのModelや利用目的に現れるDomain上の判断、計算、状態変化を指す。

Domainは、`domain/`や`domain.py`の中だけに存在するものではない。ファイル名はDomain全体の所在を宣言しない。

例えば、Jobのどの利用目的でも守る状態遷移は、Job Data Componentの`domain.py`へ置ける。一方、見積作成時にだけ成立する価格判断は、`feature/create_quote/pricing_policy.py`へ置ける。その判断がDomain上の知識であることと、Data Componentの`domain.py`に置かれることは別である。

### 配置例

```text
data_component/
    job/
        domain.py

feature/
    create_quote/
        usecase.py
        pricing_policy.py

entry/
    web/
        complete_job.py
```

- `data_component/job/domain.py`は、Jobの状態と同一性を中心に共有されるDomain Modelを置く
- `feature/create_quote/pricing_policy.py`は、Create Quoteという利用目的に固有のDomain Logicを置く
- `entry/web/complete_job.py`はHTTP入力の解釈を置く

日付文字列がISO形式かを確かめるのはWeb入力の判断になり得る。Scheduleの終了日が開始日より前ではならないという条件は、入力経路を越えて成立するDomain上の判断になり得る。同じValidationという語でも、何についての判断かが異なる。

### 利点、代償、不要な場合

Domainを配置名から分けると、Domain Logicを必ず`domain.py`へ移すという機械的な判断を避けられる。複数Featureから同じ状態と規則が観測されたならData Componentへ置き、一つのFeatureに固有ならFeatureへ残す、という判断ができる。

`domain.py`を使う利点は、親概念の内部で、状態や規則を永続化、公開操作、外部変換と区別できることである。親Packageの意味が十分であり、内部役割も一つしかないなら、専用の`domain.py`は不要である。

Domainという語を、Databaseを使わないコード、Frameworkをimportしないコード、業務担当者が話したコードのいずれか一つだけで定義しない。これらは判断材料にはなるが、Domainの所在を自動的には決めない。

## 3. Layerは配置先ではなく依存と責任の見方である

### 概念と解釈

Layered ArchitectureやClean Architectureでは、Presentation、Application、Domain、InfrastructureなどのLayer名が使われる。

- Presentation Layerは、外部入力と出力表現を扱う
- Application Layerは、利用目的と処理の協調を扱う
- Domain Layerは、Domain Modelと規則を扱う
- Infrastructure Layerは、Database、Network、Filesystem、Frameworkなどの技術実装を扱う

これらは有用な責任の見方だが、必ず同名のトップレベルフォルダにしなければならないわけではない。

### 本書の基本構造との関係

| 本書の親概念 | 含み得るLayer上の役割 |
| --- | --- |
| Data Component | Domain Model、公開操作、Repository実装、永続化変換 |
| Feature | Application Service、Feature固有のDomain Logic、Query、局所Adapter |
| Entry | Presentation、外部入力変換、Entry固有のUseCase |
| External Service等の兄弟概念 | Client、Gateway、Adapter、技術固有の失敗制御 |

したがって、`data_component/job/`の中にDomain上の`domain.py`とInfrastructure上の`repository.py`が同居する場合がある。

```text
data_component/
    job/
        domain.py
        service.py
        repository.py
```

物理的に近いことと、Domain ObjectがDatabase実装へ依存することは同じではない。実際の依存はimportと呼び出しで確認する。`domain.py`が`repository.py`をimportしなければ、Jobの状態と規則は永続化実装へ直接依存しない。

一方、`service.py`内の`Dependencies.default()`が`DefaultJobRepository`をimportして選ぶなら、そのModuleには標準実装を選ぶ責任と具体実装への依存が存在する。この事実を、フォルダの近さから隠さない。厳格な内向き依存を物理Module単位で維持したい場合は、実装選択を外側のComposition Moduleへ移せる。

### Layerをフォルダにする場合

次の構造も選択できる。

```text
presentation/
application/
domain/
infrastructure/
```

Layerごとの依存制約を強く示したい、Frameworkがこの構造を前提とする、複数の業務概念をLayer単位で横断して変更する、といった条件があるなら意味を持つ。

一方、Jobに関するコードを調べるために四つのLayerを横断する必要が生じる。役割によるまとまりと、意味によるまとまりのどちらを物理構造へ強く表すかという選択になる。

Layer名を使わないことと、責任や依存を混ぜることは同じではない。反対に、Layerフォルダを作っても、Application ServiceへSQLとHTTP変換を置けば境界は成立しない。

## 4. Composition Root、Dependency Injection、IoC Containerを分ける

### 概念と解釈

Dependency Injectionは、利用側が必要とする依存を外部から受け取ることである。普通の引数で渡すだけでも成立する。

Inversion of Controlはより広い概念であり、処理の呼び出しやlifecycleの主導権をFrameworkや別の仕組みに渡すことを含む。

IoC Containerは、型や設定からObjectの生成、解決、lifecycleを自動化する仕組みである。

Composition Rootは、Applicationを実行可能にするために、具体実装とResourceを選び、組み立て、実行入口へ接続する場所である。用語上は一つの実行物に対するRootを指すことが多いが、Web、CLI、Batchごとに別のComposition pointを持つことはできる。

### Compositionを四つの責任へ分ける

Compositionという語に、異なる責任をまとめすぎない。

| 責任 | 問い | 例 |
| --- | --- | --- |
| 実装選択 | 通常どの実装を使うか | `DefaultJobRepository`を選ぶ |
| 生成 | どこでObjectやResourceを作るか | Connection Poolを起動時に作る |
| lifecycle | いつ共有し、破棄するか | PoolをProcess停止時にcloseする |
| 受け渡し | 利用場所へどう届けるか | Request単位ConnectionをUseCaseへ渡す |

上から渡すこと自体は、選択や生成まで中央へ集約したことを意味しない。Module内でFactoryを呼ぶこと自体も、Resourceを毎回生成していることを意味しない。

### Local Defaultとの関係

本書のModule localな`Dependencies.default()`は、各Moduleが通常利用する直接依存を近傍で選ぶ方法である。

```python
@dataclass(frozen=True, slots=True)
class Dependencies:
    repository: JobRepository

    @classmethod
    def default(cls) -> Self:
        return cls(repository=DefaultJobRepository())
```

これはIoC Containerではない。また、一般にいうComposition Rootそのものとも限らない。Moduleの通常選択と、Application全体のResource構成を区別する。

```text
entry/
    web/
        app.py               # Poolや長寿命Clientの生成・破棄

feature/
    complete_job/
        usecase.py           # 直接依存と通常選択

external_service/
    mail/
        adapter.py
```

Database Poolの生成と破棄はWeb Applicationのlifecycleで扱い、Request単位のConnectionをUseCaseへ渡せる。Repository実装の標準選択はJob Module近傍に置ける。

### Composition Rootに固有ではない効果

Connection Factoryが接続設定、Poolからの取得、返却を正しく扱うなら、そのFactoryを個別Moduleから呼んでも、Rootから呼んでも、得られるConnectionの機能は同じになり得る。Factoryの責務は、呼出場所を変えただけでは増減しない。

Composition Rootへ集める利点は、接続能力そのものより次にある。

- 長寿命Resourceを一度だけ生成し、確実に破棄する
- Application起動時に設定とObject graphをまとめて検証する
- scopeと共有範囲を実行入口で決める
- 通常構成を一つの経路から追跡する
- 実行物ごとの差を比較する

同じ性質を、共有Provider、Framework lifecycle、複数のComposition Moduleで実現することもできる。Composition Rootという名前だけに固有の魔法ではない。どの責任をどの場所へ置いたかで評価する。

### 利点、代償、不要な場合

IoC Containerは、Object graphが大きい、Request scopeなどのlifecycleが複数ある、Framework統合が必要、同じ構成規則を自動化したい場合に有効である。

代償として、依存解決が実行時まで見えにくい、登録を別に追う、失敗が起動時まで分からない、といった問題がある。普通のConstructor、関数引数、`default()`で十分ならContainerは不要である。

Local DefaultはTest差し替えと通常選択を近くへ置ける一方、Module数が増えると選択や設定が散在し得る。Composition Rootは全体構成を追いやすい一方、下位の依存まで上位へ輸送するとObject graphとTest Setupが膨らむ。どちらかを名前だけで正解にしない。

## 5. CQRS、Event Sourcing、Bus、Mediatorを直接呼び出しと比較する

### CQRS

CQRSは、状態を変更するCommand側と、情報を返すQuery側の責任やModelを分ける考え方である。Read用とWrite用で異なるModel、最適化、保存形式を採用できる。

`usecase.py`と`query.py`を分けただけで、直ちにCQRSと呼ぶ必要はない。単純なCommand・Query分離は多くのApplicationに存在する。Read ModelとWrite Modelが独立して変わる、読み取り性能のため別のProjectionを持つ、更新と参照で異なる契約を維持する、といった構造的な差が強くなったときにCQRSという説明が有効になる。

CQRSは、Read DatabaseとWrite Databaseを必ず分ける規則ではない。Event Sourcingとも同義ではない。同じDatabaseを使いながら、Modelと責任だけを分けることもできる。

### Event Sourcing

Event Sourcingは、現在状態だけを保存する代わりに、状態を変化させたEventの列を記録し、その列から現在状態を再構成する方法である。Eventを発行していることや、Audit logを残していることだけではEvent Sourcingにならない。記録されたEventが状態の基準になる。

```text
data_component/
    job/
        domain.py
        event_stream.py
        repository.py

event_store/
    adapter.py
```

Event Sourcingを使うと、どの変更がどの順序で起きたかを基準データとして保持し、過去時点の再構成や新しいProjectionの再生成が可能になる。

一方、Event schemaの長期互換性、Replay、Snapshot、誤ったEventの訂正、個人情報の削除、外部I/Oとの整合性を扱う必要がある。履歴が必要であることだけを理由に導入しない。現在状態と通常の変更履歴で要求を満たせる場合は、その方が単純である。

### Command Bus、Query Bus、Mediator

BusやMediatorは、MessageからHandlerを選び、処理をDispatchする。

```text
Command -> Bus -> Handler
```

認可、Logging、Retry、Transactionなどの共通Pipeline、PluginによるHandler登録、実行時Routingが必要なら意味を持つ。

一方、呼び出し先が静的に一つなら、直接importして呼べる。

```python
from feature.complete_job import execute

execute(command)
```

Busは依存を消さない。登録規則、Message型、Handler解決、共通Middleware、失敗処理という別の依存へ変える。処理の入口と呼び出し先を追いやすくするのか、見えにくくするのかを実際の利用例で判断する。

Dispatch自体がApplication全体の独立した能力になったなら、具体名を持つ兄弟概念へ置ける。

```text
message_dispatch/
    command_bus.py
    handler_registry.py
```

一つのEntryだけがFrameworkのMediatorを使うなら、Entry内部へ閉じ込める選択もある。

## 6. SubdomainとBounded Contextを問題とModelの境界として分ける

### DomainとSubdomain

大きなDomainは、異なる問題、能力、専門知識を持つSubdomainへ分けて考えられる。

Subdomainは問題領域側の区分である。Core、Supporting、Genericなどの分類は、どこへ設計と開発の労力を集中するか、既製品や外部Serviceを利用するかを考える材料になる。そのままフォルダ名を決めるものではない。

### Bounded Context

Bounded Contextは、あるModelと言語が一貫した意味を持つ範囲である。同じ言葉でも、Contextが変われば属性、規則、同一性が変わり得る。

例えば、営業では`Customer`を契約先、担当者、商談履歴を中心に扱い、請求では`Customer`を請求先、支払条件、与信状態を中心に扱うかもしれない。同じDatabase Tableを参照しても、同じModelとは限らない。

SubdomainとBounded Contextは同義ではない。

- Subdomainは、問題をどう分けて理解するかを表す
- Bounded Contextは、どのModelと言語をどこまで一貫させるかを表す

一つのSubdomainを複数Contextで実装することも、一つのContextが複数の小さなSubdomainを扱うこともあり得る。

### 物理構造への反映

Bounded Contextは、必要な強さに応じて異なる形で具体化できる。

```text
job_management/
    data_component/
    feature/
    entry/

schedule_planning/
    data_component/
    feature/
    entry/
```

この例では、各Contextの内側で本書の基本構造を使っている。しかし、Bounded Contextは必ずこのフォルダ構造になるわけではない。

- 同じPackage内で型と公開面だけを分ける
- 一つのRepository内でトップレベルPackageを分ける
- Repositoryを分ける
- 実行ProcessやDatabaseを分ける
- Network越しのServiceに分ける

Contextが違うことと、Microserviceに分けることは同じではない。独立した配備、障害、性能、権限、Team所有が必要になったときに、実行境界を強める理由が生まれる。

同じDatabaseを使うことも、直ちに同じContextであることを意味しない。ただし、複数Contextが互いのTableへ自由に書き込み、Migrationを個別に変更するなら、Model所有と公開契約の境界は弱くなる。同じDatabase内でもTableの所有、書込み経路、Migration責任を分けられる。

### 利点、代償、不要な場合

Bounded Contextを明示すると、同じ用語へ一つの巨大なModelを強制せずに済む。ContextごとにRepository、DTO、Event、規則の意味を保てる。外部Contextとの変換が必要な場所も明らかになる。

代償として、似た型、変換、同期、所有調整が増える。単に機能が二つある、フォルダが大きい、Teamが二つあるという理由だけでは、異なるModelと言語の境界があるとは限らない。

## 7. Ubiquitous LanguageとContext Mapを境界の関係として残す

### Ubiquitous Language

Ubiquitous Languageは、Domainの専門家と開発者が、特定のBounded Context内でModelと会話に一貫して使う言葉である。用語集を作るだけではなく、コードの型、関数、Event、画面、Testにも同じ意味を反映する。

同じ単語を全社で一つの意味に統一することが目的ではない。Contextごとの差を明示することも一貫性の一部である。

Job Management Contextの`complete_job`とBatch実行基盤の`complete_job`が異なる意味を持つなら、Namespaceまたは具体名で区別する。

```python
from job_management import complete_production_job
from batch_runtime import complete_execution_job
```

ContextのNamespaceが明確なら、双方で`complete_job`を使っても意味を保てる。

### Context Map

Context Mapは、Bounded Context同士がどのような関係でModelや変更を受け渡すかを示す。単なるSystem構成図ではなく、上流・下流、言語の採用、翻訳、共同変更の関係を表す。

| 関係 | 意味 | 具体化の例 |
| --- | --- | --- |
| Partnership | 二つのContextが成功と変更計画を密接に共有する | 共同計画、共同Test、同期Release |
| Shared Kernel | 小さなModelを意図的に共同所有する | 共有Package、共同Test、version規則 |
| Customer・Supplier | 下流の要求を上流と調整する | API契約、変更協議、Contract Test |
| Conformist | 下流が上流のModelと言語へ合わせる | 内部Modelを上流語彙へ合わせる |
| Anti-Corruption Layer | 外部Modelを内部Modelへ翻訳する | Adapter、Translator、Gateway |
| Open Host Service | 複数Consumerへ安定した入口を公開する | API、Message endpoint |
| Published Language | Context間で共有する明示的な形式を定める | version付きschema、契約文書 |
| Separate Ways | 統合の価値より費用が高いため連携しない | 独立Model、重複実装、手動連携 |

### Shared Kernelを`shared/`と同一視しない

Shared Kernelは、便利な共通関数の置き場所ではない。複数Contextが同じModelの一部を共同所有し、変更に協調が必要な関係である。

```text
shared_kernel/
    money.py
    currency.py
```

この構造を採用するなら、両Contextが同じ意味とversionを受け入れる必要がある。単に二か所からimportされたことだけでShared Kernelにしない。重複を残してContextごとの意味を保つ方が安い場合もある。

### Anti-Corruption Layerの配置

外部会計SystemのModelを内部へ持ち込まないために、次の構造を置ける。

```text
external_service/
    accounting/
        client.py
        translator.py
        adapter.py
```

これは三つのファイルを必須とするPatternではない。変換が短ければ`adapter.py`一つでよい。重要なのは、外部の識別子、Status、Error、更新順序を内部Modelへそのまま拡散させないことである。

Contextが一つで、外部Serviceも単純な値を返すだけなら、Context Mapの関係名を一式導入する必要はない。翻訳、共同所有、version調整が設計問題になったときに具体化する。

## 8. Workflow、State Machine、Process Manager、Sagaを時間をまたぐ境界として置く

### 概念と解釈

一つのUseCaseは、通常、一つの利用目的が完了するまでの処理を表す。しかし、処理が複数のEvent、待機、外部System、Transactionをまたぐと、一回の関数呼び出しだけでは完了を表せない。

- Workflowは、複数Stepと分岐を含む処理の進行を表す
- State Machineは、状態と許可される遷移を明示する
- Process Managerは、Eventを受け、進行状態を保持し、次のCommandを決める
- Sagaは、複数のTransactionをまたぐ処理と、必要な補償を扱う

Sagaという語は、Orchestration型とChoreography型を含め、資料によって使い方が異なる。少なくとも、一つのDatabase Transactionへ収まらない変更を、失敗と補償を含めて進める責任があるかを確認する。

### 配置例

Feature内部の数Stepとして完了するなら、Feature配下へ置ける。

```text
feature/
    fulfill_job/
        usecase.py
        workflow.py
```

複数Contextをまたぎ、長期間状態を保持する独立したProcessなら、兄弟概念として置ける。

```text
process/
    job_fulfillment/
        state.py
        process_manager.py
        repository.py
```

`process/`は四つ目の固定分類ではない。Job Fulfillmentという長期Processが、個別FeatureやData Componentの配下では説明できない独立した意味を持ったため追加する。

```python
def handle(event: PaymentConfirmed, state: FulfillmentState) -> list[Command]:
    state.mark_payment_confirmed()
    if state.can_start_production():
        return [StartProduction(job_id=state.job_id)]
    return []
```

Process Managerの状態を保存するRepositoryは、Job AggregateのRepositoryとは別の意味を持つ。何が完了し、何を待ち、どのCommandを発行済みかを保存する。

### 実行上の責任

長期Processでは、次を扱う必要がある。

- Eventの重複とIdempotency
- 配送失敗とRetry
- 順序の入替え
- Process状態の永続化
- Command発行と状態保存の整合性
- Timeoutと人による再開
- 補償が可能な操作と不可能な操作
- version更新中のProcess継続

OutboxやInboxは、Database変更とMessage配送の間を扱う具体策になり得る。これらはSagaという名前を付ければ自動的に解決するものではない。

一つのUseCase内で順番に関数を呼び、同じTransactionで完了できるならWorkflow EngineやSagaは不要である。関数が三つあることと、分散Transactionがあることを同一視しない。

## 9. 境界の強さを観測した差に合わせる

同じ概念の違いでも、必要な境界の強さは異なる。

| 観測した差 | 最小限の具体化 | より強い境界が必要な場合 |
| --- | --- | --- |
| 処理の役割が違う | 関数、Class、Module名 | 独立した公開面とTestを持つPackage |
| 親となる意味が違う | 兄弟Module・Package | import制約、所有者の分離 |
| Modelと言語が違う | Namespace、DTO、Translator | Bounded Context Package、Contract Test |
| 変更とReleaseが独立する | Repository内のComponent | Repository分割、version付き契約 |
| Resourceや障害範囲が違う | 同一Process内のAdapter | 別Process、Network境界 |
| 性能・権限・運用責任が違う | 設定と実行入口の分離 | 独立Deployment、Database分離 |

最も強い境界を最初から選ぶことが、最も適切とは限らない。Network境界はimportを禁止できる一方、通信失敗、version管理、監視、配備調整を追加する。単一Packageは変更しやすい一方、規約だけでは境界を越えた参照を防げない。

境界の強さは、次の問いで決める。

1. 誤った参照をReviewで防げるか、仕組みで禁止する必要があるか
2. 同時に変更・Releaseできるか
3. 同じProcessとDatabaseを共有しても障害や性能の要求を満たせるか
4. 誰がModelと契約を変更する責任を持つか
5. 移動、変換、同期、運用の追加費用を受け入れられるか

構造変更には、import、Test、Migration、運用、Team間調整の費用が生じる。用語が大きいから強い境界を選ぶのではなく、現在必要な制約と、変更時に支払える費用を対応させる。

## 10. 一つのApplication断面へ尺度を重ねる

ここまでの語彙を、Job管理、Schedule計画、会計連携、長期的なJob Fulfillmentを持つApplicationへ重ねる。

```text
job_management/
    data_component/
        job/
            domain.py
            repository.py
            service.py
    feature/
        complete_job/
            usecase.py
            command.py
    entry/
        web/
            complete_job.py
    external_service/
        accounting/
            client.py
            translator.py
            adapter.py

schedule_planning/
    data_component/
        schedule/
            domain.py
            allocation_policy.py
    feature/
        reschedule_job/
            usecase.py
            query.py
    integration/
        job_management/
            gateway.py
            translator.py

process/
    job_fulfillment/
        state.py
        process_manager.py
        repository.py
```

| 構造 | 語彙 | 具体化した判断 |
| --- | --- | --- |
| `job/domain.py` | Domain Model、Entity、Aggregate | Job Management内で一貫するJobの状態と規則 |
| `complete_job/usecase.py` | UseCase、Application Service | Complete Jobの成功までの処理 |
| `accounting/translator.py` | Translator、Anti-Corruption Layer | 会計ModelとJob Management Modelの翻訳 |
| `job_management/` | Bounded Context候補 | JobというModelと言語を保つ範囲 |
| `schedule_planning/` | Bounded Context候補 | Schedule計画固有のModelと言語を保つ範囲 |
| `integration/job_management/` | Gateway、Translator | Context間の公開契約を接続する |
| `process/job_fulfillment/` | Process Manager、Saga候補 | 複数ContextとTransactionをまたぐ進行状態 |

この構造だけで、二つのBounded ContextやSagaが成立したと断定はできない。Modelと言語が本当に異なるか、独立した公開契約があるか、Processが複数Transactionと待機をまたぐかを観測する必要がある。

## 11. より広い概念を採用するときの確認事項

1. **尺度** — Module、Application、Domain、Process、Deploymentのどれを扱う語か
2. **区別** — その用語によって何と何を分けるのか
3. **観測事実** — 異なるModel、言語、lifecycle、所有、Release、障害範囲が実在するか
4. **公開面** — 境界の外へ何を公開し、何を内部に残すか
5. **依存** — どのModuleやContextが、どの契約を直接利用するか
6. **物理的な強さ** — 名前、Package、Repository、Process、Networkのどこまで分けるか
7. **運用責任** — 設定、Resource、version、監視、障害対応を誰が持つか
8. **代償** — 型、変換、同期、配備、調整がどれだけ増えるか
9. **不要条件** — 普通の関数、直接呼び出し、同一Model、同一Processで十分ではないか

用語の定義に一致していても、専用の型やフォルダが必要とは限らない。反対に、その用語を使わなくても、同じ区別を具体名、公開面、依存制約で表せる場合がある。

## 12. この章の結論

LayerやComposition RootはApplicationの責任と依存構成を扱い、Bounded ContextやContext MapはModelと言語の境界を扱い、Process ManagerやSagaは時間とTransactionをまたぐ進行を扱う。

これらを具体化するとは、用語と同名の大きなフォルダを作ることではない。現在観測できるModel、言語、依存、lifecycle、所有、実行条件を、必要な強さのNamespace、公開面、契約、Process、Deploymentへ反映することである。

より広い概念ほど、導入後の変換、同期、version、運用の費用も増え得る。既存語彙は境界を自動決定するものではなく、何を区別し、その区別をどの構造と制約で維持するかを共有するために使う。
