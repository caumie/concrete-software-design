# 第7章　依存を利用する場所で明示する

## この章の目的

依存関係を、Module間の直接利用として捉える。上位から下位までを一つのDependency構造へ写し替えず、それぞれのModuleが直接利用するものだけを明示し、同じ境界でTestする。

あわせて、実装の選択、ObjectやResourceの生成、lifecycle、利用場所への受け渡しを分ける。Local DefaultとComposition Rootの差を、どこからFactoryを呼ぶかだけではなく、何を決め、何を生存させるかで説明する。

## 1. 依存グラフは直接利用の関係である

Pythonでは、どのModuleがどの公開要素をimportし、利用しているかが依存関係として現れる。

```python
from data_component.job import complete_job
from external_service.mail import send_completion_mail
```

UseCaseがこれらを呼ぶなら、Jobの公開操作とMail送信がUseCaseの直接依存である。

Job内部のRepositoryは、Job側Moduleの直接依存である。UseCaseがRepositoryを直接利用しないなら、UseCaseのDependencyではない。

依存関係を明示するとは、Application全体のObject graphをすべてのModuleへ渡すことではない。利用している関係を、その利用場所から追えるようにすることである。

## 2. 単純な引数で十分ならそのまま使う

Dependency InjectionはContainerを必要としない。

```python
def calculate_deadline(start_date, calendar) -> date:
    ...
```

と引数で渡すだけでも、利用側が外部要素を受け取っている。

依存が一つで、標準構成やまとまりを表す必要がなければ、専用のDependency型を作らなくてよい。関数を直接importしてよく、差し替える必要もないなら、引数化そのものが不要な場合もある。

## 3. 複数の直接依存を型として表す

直接依存が複数あり、Test差し替えや標準構成の入口が必要なら、一つの型へまとめられる。

```python
@dataclass(frozen=True, slots=True)
class Dependencies:
    connection: Connection
    complete_job: CompleteJob
    send_notification: SendNotification
```

この型はApplication全体の依存一覧ではない。現在のModuleが何を直接必要としているかを表す。

利用側が必要とする呼び出し方を型として正確に表したい場合は、`Callable`や`Protocol`を使える。依存だから必ずInterfaceを作るわけではない。

`Dependencies`へまとめるか、個別のKeyword-only引数にするかは、依存数、標準構成、Test Setup、呼び出しの読みやすさで決める。

## 4. 下位Moduleの依存を上位へ輸送しない

次の呼び出し関係を考える。

```text
feature/complete_job.py
        ↓
data_component/job/service.py
        ↓
data_component/job/repository.py
```

FeatureはJobの公開操作を利用する。Job ServiceはRepositoryを利用する。

次のように、下位の依存を上位の型へ階層化しない。

```python
@dataclass
class CompleteJobDependencies:
    job: JobDependencies
```

また、Featureが直接使わないJob Repositoryを、Featureの`Dependencies`へ追加しない。

各Moduleは、自分の直接依存だけを自分の近くで明示する。下位Moduleの通常構成を上位が毎回組み立てる必要はない。

## 5. 依存設計を四つの判断へ分ける

依存の構成には、少なくとも四つの判断がある。

1. **選択** — どの実装を標準として使うか
2. **生成** — ObjectやResourceをどこで作るか
3. **lifecycle** — いつ作り、いつ共有し、いつ破棄するか
4. **受け渡し** — 利用するModuleへ、どの経路で値や能力を渡すか

上位から引数を渡すことは、選択、生成、lifecycleまで上位へ集約したことを必ずしも意味しない。

反対に、Module近傍で実装を選んでも、Connection PoolやClientの生成元はApplicationの実行入口にあるかもしれない。

「中央集権」「局所化」という一語でまとめず、何をどこで決めているかを分けて記述する。

## 6. 値を必要とするか、生成・取得能力を必要とするか

UseCase実行中に一つのConnectionを使うだけなら、生成済みのConnectionを受け取れる。

```python
@dataclass(frozen=True, slots=True)
class Dependencies:
    connection: Connection
```

UseCase自身がConnectionの取得時点やTransaction開始を決める必要があるなら、取得能力を受け取る意味がある。

```python
class AcquireConnection(Protocol):
    def __call__(self) -> ContextManager[Connection]:
        ...


@dataclass(frozen=True, slots=True)
class Dependencies:
    acquire_connection: AcquireConnection
```

Factory、Provider、Resolverを抽象化の形式として先に作らず、利用側が完成した値を必要とするのか、生成・取得・選択の能力を必要とするのかで決める。

## 7. 長寿命Resourceと一回の利用を分ける

Database接続では、少なくとも二つのlifecycleがある。

| 対象 | 代表的なlifecycle | 主な責任 |
| --- | --- | --- |
| Connection Pool | Process起動から停止まで | 設定、生成、共有、health、破棄 |
| Connection | RequestまたはUseCase単位 | Poolから取得、Transaction、返却 |

Poolを使うFactoryは、接続設定や取得方法を一か所に持てる。しかし、そのFactoryをComposition Rootから呼ぶか、個別Moduleから呼ぶかによって、Factory自身の責任が変わるわけではない。同じFactoryと同じPoolを使うなら、Connectionを得る機能上の効果は同じになり得る。

Composition側へ置くことで増えるのは、主に次の性質である。

- 長寿命Resourceを一度だけ生成し、停止時に破棄する場所を追いやすい
- Application起動時に設定と構成をまとめて検証できる
- Web、CLI、Batchごとのscopeを入口で決められる
- 実行経路全体で何を共有しているかを一覧しやすい

一方、個別Moduleから同じProviderを呼んでも、Providerが共有Poolを正しく保持していれば、Resource再利用は成立する。違いは能力の有無ではなく、構成の追跡、検証、scopeの決定場所にある。

したがって、長寿命Resourceの生成・破棄は実行入口のlifecycleへ置き、一回のConnectionはEntryまたはUseCaseの必要な境界で取得する、という形を初期候補にできる。

```text
entry/web/app.py          # Poolを生成・破棄する
entry/web/request.py      # Request単位でConnectionを取得する
feature/complete_job.py   # Connectionを直接利用する
```

FrameworkがRequest単位のConnectionを既に管理するなら、それをUseCaseへ渡せる。UseCase自身がTransaction scopeを持つなら、共有Poolへ接続された`acquire_connection`を直接依存にできる。

## 8. Local Defaultと外側のCompositionを競合させない

Module近傍の`Dependencies.default()`は、そのModuleが通常利用する直接依存を選ぶために使える。

```python
@dataclass(frozen=True, slots=True)
class Dependencies:
    complete_job: CompleteJob

    @classmethod
    def default(cls) -> Self:
        return cls(complete_job=complete_job_default)
```

この`default()`は、Application全体の長寿命Resourceまで作る必要はない。Repository実装や通常の関数を選び、PoolやClientは外側で構成されたProviderから得ることができる。

外側のCompositionは、実行可能な構成とlifecycleを作る。Local Defaultは、Moduleの通常選択とTest差し替えの入口を作る。両者が扱う判断を分ければ、併用できる。

ただし、複数の`default()`が同じ設定値、Client生成、実装選択を重複し始めたなら、局所化ではなく散在になっている可能性がある。Application全体の構成をどこから追うか、起動時に何を検証するかを別に用意する。

## 9. 条件分岐はまず条件分岐として書く

実装選択が一箇所だけにあるなら、単純な分岐で表現できる。

```python
if command.preview:
    sender = preview_sender
else:
    sender = normal_sender
```

同じ選択理由が複数箇所へ現れ、独立した意味を持つと分かったときに、ResolverやFactoryへ名前を与えられる。

分類名を先に作る必要はない。

## 10. Module単体Testでは直接依存を差し替える

Complete Job UseCaseのTestでは、UseCaseが直接利用するJob操作とConnectionを差し替える。

```python
calls: list[int] = []


def fake_complete_job(job_id: int, connection) -> None:
    calls.append(job_id)


dependencies = Dependencies(
    connection=fake_connection,
    complete_job=fake_complete_job,
    send_notification=fake_notification,
)
```

Job内部のRepositoryまで同じTestで構成しない。Job側はJob側のModule TestでRepositoryを差し替える。

このTest境界はProductionの直接利用関係と同じである。

## 11. Default wiringとResource lifecycleを別にTestする

直接依存を差し替えたModule Testは、処理順序と判断を確認できる。しかし、通常構成が正しく選ばれること、Poolが一度だけ生成されること、Connectionが返却されることまでは保証しない。

確認対象を分ける。

- Module Test — 直接依存を差し替え、処理と判断を確認する
- Construction Test — `default()`やCompositionが必要なObjectを作れるか確認する
- Integration Test — Databaseや外部Clientと契約どおり接続できるか確認する
- Lifecycle TestまたはSmoke Test — 起動、共有、停止、代表経路を確認する

Test Setupの大きさは判定条件ではない。一つのModule TestにApplication全体の構成が必要なら、直接利用していない依存まで渡していないかを再評価する観測点になる。

## 12. 依存定義と実装共有を分ける

複数Moduleが同じClock実装を使っていても、すべてのDependency fieldを一つの共通`Dependencies`へ統合する必要はない。

```python
@dataclass(frozen=True, slots=True)
class CompleteJobDependencies:
    clock: Clock


@dataclass(frozen=True, slots=True)
class CreateScheduleDependencies:
    clock: Clock
```

標準実装として同じ`system_clock`を使うことと、利用側のDependency型を共有することは別である。

同じConnection Poolを使うことも、すべてのUseCaseが同じConnectionや同じTransactionを共有することを意味しない。

## 13. 例: Reschedule Jobの直接依存

Request単位でConnectionを得る構成なら、UseCaseは完成したConnectionを直接受け取れる。

```python
@dataclass(frozen=True, slots=True)
class Dependencies:
    connection: Connection
    ensure_reschedulable: EnsureReschedulable
    change_period: ChangePeriod


def execute(command, *, dependencies: Dependencies) -> None:
    dependencies.ensure_reschedulable(
        command.job_id,
        dependencies.connection,
    )
    dependencies.change_period(
        command.schedule_id,
        command.period,
        dependencies.connection,
    )
    dependencies.connection.commit()
```

UseCaseはJobとScheduleの公開操作、Connectionだけを直接利用する。Job RepositoryとSchedule Repositoryは、それぞれのData Component内部で明示する。

Poolはここへ渡さなくてもよい。UseCaseがConnection取得時点を決める要件が生じたときに、`connection`を`acquire_connection`へ変更する理由ができる。

## 14. この章の結論

依存は、Module間の直接利用として捉える。普通の引数で十分ならそのまま使い、必要ならModule localな型で直接依存をまとめる。

下位Moduleの依存を上位へ輸送しない。実装の選択、ObjectやResourceの生成、lifecycle、値や能力の受け渡しを分けて考える。

Composition RootからFactoryを呼ぶこと自体に、個別Moduleから同じFactoryを呼ぶ場合にはない接続能力が生まれるわけではない。長寿命Resourceの一貫した生成・破棄、scope、起動時検証、全体構成の追跡が必要なときに、外側のCompositionへ集める意味がある。Module単体Testでは直接依存を差し替え、通常構成とResource lifecycleは別のTestで確認する。
