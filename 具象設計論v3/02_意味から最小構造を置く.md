# 第2章　意味から最小構造を置く

## この章の目的

現在説明できる意味を、まだ決めすぎない最小のModuleとPackageへ置く。`data_component / feature / entry`を初期値として使いながら、役割名による先回り、過剰なフォルダ化、閉じた三分類を避ける。

Applicationが`app.py`一つから成長する時系列は、次の第3章から扱う。本章は、その事例へ入る前に、ある時点で観測できる意味と配置の関係を示す。

## 1. 概念は一つのModuleから始められる

新しい意味が一つのファイルで説明できるなら、最初からフォルダを作る必要はない。

```text
feature/
    create_job.py
```

内部に異なる役割が現れたとき、同名Packageへ成長させられる。

```text
feature/
    create_job/
        __init__.py
        usecase.py
        preview.py
```

概念を区別することと、その概念のために複数のファイルを作ることは別である。Moduleで十分な段階に、`command.py`、`handler.py`、`service.py`、`repository.py`を一式作らない。

## 2. 最初の三つの親概念

業務Applicationでは、比較的早い段階で次の違いが現れやすい。

```text
data_component/
feature/
entry/
```

- `data_component/`は、何を保持・参照・変更するか
- `feature/`は、何を達成するか
- `entry/`は、どの外部経路から利用されるか

例えば、Jobの状態、Jobを完了する利用目的、Webからの入口を区別できるなら、次の配置を候補にできる。

```text
data_component/
    job.py
feature/
    complete_job.py
entry/
    web.py
```

これは完成したArchitectureではない。現在説明できる大きな意味に名前を与え、後から観測できる配置にした初期値である。

## 3. 役割より親となる意味を先に置く

Repository、Query、UseCase、Controller、Adapterは、コードの役割を表す。

Job、Complete Job、Web、Mailは、コードをまとめる親概念になり得る。

Repositoryという役割が見えたことだけを理由に、次のトップレベル構造を作る必要はない。

```text
repository/
    job_repository.py
```

Jobの復元と保存を扱うなら、Jobという親概念の内部役割として置ける。

```text
data_component/
    job/
        domain.py
        repository.py
```

一方、Application全体の保存境界として一つの`repository.py`を公開する意味が実在するなら、Application直下へ置く選択もできる。初期値は「Repositoryだからここ」ではなく、「何についてのRepositoryか」を先に決めることである。

## 4. 横への追加と縦への深掘り

新しい利用目的が増えたら、兄弟として追加できる。

```text
feature/
    create_job.py
    complete_job.py
    reschedule_job.py
```

一つのFeature内部に異なる役割が現れたら、同名Packageへ深掘りできる。

```text
feature/
    complete_job/
        __init__.py
        usecase.py
        preview.py
```

Data ComponentやEntryも同じように成長できる。

```text
data_component/
    job.py
    schedule.py

entry/
    web.py
    cli.py
```

横と縦のどちらへ進むかは、増えた意味によって判断する。ファイル数だけでは決めない。

## 5. 配下・利用・実行順序を同一視しない

次の配置を考える。

```text
data_component/
    job/
        domain.py
        repository.py
feature/
    complete_job.py
```

`repository.py`がJob配下にあることは、Job EntityがRepositoryを呼ぶことを意味しない。`complete_job.py`がJobの公開操作を利用することは、Complete Jobの配下にJobを置くことを意味しない。

物理的な配下、importによる利用、実行時の呼び出し順序は別の関係である。フォルダtreeだけから依存方向を推測せず、公開面とimportも確認する。

## 6. 三つの分類を閉じた型にしない

外部サービス固有の通信、認証、変換、失敗制御が独立した意味を持つなら、兄弟概念を追加できる。

```text
external_service/
    stripe.py
```

複数のTransactionと待機をまたぐ進行状態が独立した意味を持つなら、長期Processを追加できる。

```text
process/
    job_fulfillment.py
```

管理機能が一般機能と異なる利用者、権限、変更理由を持つなら、具体名を持つ別の親概念を作れる。

`data_component / feature / entry`はブートストラップであり、すべてのコードを押し込む閉じた分類ではない。

## 7. 名前は配下を検討する手掛かりになる

`entry/web/`と名付けたなら、その配下のコードがWebという入口なしでも同じ意味で成立するかを確認できる。

`data_component/job/`と名付けたなら、その配下のコードをJobという意味で説明できるかを確認できる。

```text
entry/
    web/
        import_job.py
```

後からCLIでも同じImport処理が必要になり、HTTPやUploadから独立した利用目的と分かったなら、次の配置を検討できる。

```text
feature/
    import_job.py
```

利用箇所が二つになったから移すのではない。Webという親概念がなくても同じ意味で成立すると判断したため移す。

一般的な語と異なる定義を必要とする名前より、プロジェクトで意味を説明できる具体名を優先する。初期値の名前を後から変えることもできるが、import、Test、文書、運用手順の更新費用は発生する。

## 8. 初期構造が保証しないこと

この構造だけでは、適切なData Component境界もFeature境界も決まらない。

```text
data_component/
    everything.py
```

のような巨大な概念も作れてしまう。反対に、細かすぎるFeatureを大量に作ることもできる。

初期構造が提供するのは、発見した概念を配置し、後から更新できる余地である。Domainの発見、境界判断、変更費用の消滅を保証しない。

## 9. 配置を決める最小の問い

新しいコードを置くとき、まず次を確認する。

1. 何を完了するコードか
2. 何についての状態、規則、変換、通信か
3. 既存の親概念の配下で説明できるか
4. 親概念がなくても同じ意味で成立するか
5. 一つのModuleで十分か
6. 別概念から何を利用させるか
7. どの事実が増えたら配置を見直すか

この問いから一意の答えが出るとは限らない。候補の差と暫定判断を残し、実装後に俯瞰できる状態を作る。

## 10. この章の結論

現在説明できる意味を一つのModuleとして置き、内部役割が増えたときにPackageへ成長させる。

`data_component / feature / entry`は、意味あるデータ、利用目的、外部からの経路を区別する初期値である。役割名より親となる意味を先に置き、横への追加と縦への深掘りを受け入れる。三分類も名称も固定せず、実装で得た事実に応じて更新する。
