# 第13章　使われづらい用語と本書での対応

## この章の目的

設計資料では見かけるものの、本書の構造では専用のトップレベルフォルダ、Class、Moduleとして現れにくい用語を整理し、どのコードにその役割が成立するかを対応づける。

ここで「使われづらい」とは、一般に利用例が少ない、または価値が低いという意味ではない。次のいずれかを指す。

- 複数の意味で使われ、名前だけでは配置を決めにくい
- 一つの関数やModuleが別の役割と兼ねるため、専用部品にしなくてよい
- 本書では`feature/complete_job.py`のような具体名を先に使うため、一般的な役割名がファイル名に現れにくい
- 役割は存在しても、型やフォルダとして明示するほどの差がまだない

例えば、Featureの`execute()`はUseCaseであると同時にCommand Handler、Interactor、Orchestratorになり得る。`entry/web/complete_job.py`はControllerであると同時にInbound Adapterになり得る。用語ごとに転送Classや重複ファイルを作る必要はない。

本章は、用語を使わない理由を並べる章ではない。一般的な語が区別している責任を確認し、本書の具体名、配置、公開面、依存へ接続する章である。

## 1. 対応関係は一対一ではない

本書の親概念と既存の役割には、次のような重なりがある。

| 本書の構造 | 成立し得る既存語彙 | 専用部品を作る判断 |
| --- | --- | --- |
| `feature/<purpose>.py` | UseCase、Application Service、Command Handler、Interactor、Orchestrator | 内部役割が増えたときにPackage化する |
| `entry/web/<purpose>.py` | Controller、HTTP Handler、Inbound Adapter、Request Mapper、Presenter | 入力と出力の変換が独立して複雑になったときに分ける |
| `data_component/<name>/service.py` | 公開操作、Facade、Repository Portの利用側 | 複数の公開操作や内部協調が現れたときに分ける |
| `data_component/<name>/repository.py` | Repository、DAOの一部、Data Mapper、Persistence Adapter | 対象の復元・保存とTable操作のどちらが中心かを見る |
| `external_service/<name>/adapter.py` | Outbound Adapter、Gateway、Translator、Client wrapper | 通信、変換、内部向け契約の差が独立したときに分ける |
| `feature/<purpose>/query.py` | Query Handler、Read Model Builder、DAO利用側 | 読み取り目的と結果の形が独立したときに作る |
| `Dependencies.default()` | Factory、Provider、Resolver、Composition function | 選択、生成、lifecycleのどこまで持つかを明示する |

この表は名前の置換表ではない。同じコードに複数の説明が成立し、どの説明を名前に出すかは親概念と現在の責任で決まる。

## 2. ModelとSchemaを具体名へ分解する

### 概念と解釈

`Model`と`Schema`は、多くのFrameworkやLibraryが異なる意味で使う一般語である。

`Model`には、少なくとも次がある。

- Domainの概念と規則を表すDomain Model
- ORMがDatabase Tableとの対応を表すPersistence Model
- 読み取り目的に合わせたRead Model
- 画面表示と操作状態に合わせたView Model
- HTTP入力や出力を表すRequest・Response Model

`Schema`にも、Database Schema、API Schema、Event Schema、Validation用の型などがある。

そのため、トップレベルの`models.py`や`schemas.py`は、Applicationが成長すると異なる意味を集めやすい。

### 配置例

```text
data_component/
    job/
        domain.py              # Domain Model
        repository.py          # Persistence Modelとの変換

feature/
    list_jobs/
        query.py               # Read Model

entry/
    web/
        complete_job.py        # Request・Response Model

external_service/
    event_bus/
        job_completed_v1.py    # Integration Event Schema
```

ORM ModelがJob Repositoryだけで使われるなら、`repository.py`の非公開型として置ける。複数の永続化Moduleが同じTable表現を利用し、Database上のModelとして独立した意味を持つなら、`persistence_model.py`などへ分けられる。

Pydanticの`BaseModel`を継承していることは、その型がDomain Modelであることを意味しない。何の契約を表しているかによって、Request Model、Response Model、設定Model、外部Schemaなどを判断する。

### 利点、代償、不要な場合

具体名へ分けると、同じ「Model」という名前の下で、Domain規則、Database都合、画面都合が混ざることを避けられる。

ただし、親Packageによって意味が一意なら、短い名前を使える。一般語を禁止するのではなく、親概念を含めても意味が曖昧かを見る。

## 3. Command、Handler、Interactorを利用目的へ置く

### Command

Commandは、状態を変更してほしいという意図を表す。Queryが情報の取得を表すのに対し、Commandは達成したい変更を表す。

Commandはデータを運ぶDTOでもあり得るが、すべてのDTOがCommandではない。`CompleteJobCommand`にはJobを完了させる変更意図がある。`JobListItem`はデータを運ぶが、変更意図はない。

```python
@dataclass(frozen=True, slots=True)
class CompleteJobCommand:
    actor_id: int
    job_id: int
    reason: str
```

引数が`job_id: int`一つで意味が十分なら、Command型を作る必要はない。複数Entryが同じFeatureを利用する、入力契約をversion管理する、Messageとして配送するといった条件があるときに価値が増える。

### Handler

Handlerは、Command、Query、Event、HTTP Requestなどを受けて処理する役割である。何を処理するHandlerかを親概念と入力の種類で区別する。

```text
feature/
    complete_job/
        usecase.py

entry/
    web/
        complete_job.py
    message_consumer/
        complete_job.py
```

Web HandlerとMessage Handlerは、異なる外部入力を同じFeatureのCommandへ変換できる。Featureの`execute()`はCommand Handlerとして動くが、`handlers/complete_job_handler.py`へ移す必要はない。

### Interactor

Clean Architectureで使われるInteractorは、UseCaseを実行するObjectを指すことが多い。本書では、Featureの`execute()`関数がUseCase、Application Service、Command Handler、Interactorの複数の役割を同時に持ち得る。

```python
def execute(command: CompleteJobCommand) -> CompleteJobResult:
    ...
```

関数の公開契約で十分なら、`CompleteJobInteractor` Classを別に作る必要はない。状態を保持する、複数実装を切り替える、FrameworkがObjectを要求する、といった理由があるときにClass化できる。

### Input BoundaryとOutput Boundary

UseCaseへCommandを渡す契約はInput Boundaryとして説明できる。UseCaseが結果を返す契約やPresenterを呼ぶ契約はOutput Boundaryとして説明できる。

Pythonでは、公開関数と戻り値の型だけで契約を表せる場合がある。複数実装、Frameworkによる接続、詳細な型検査が必要なら`Protocol`を置ける。

Input Port、Interactor、Command Handlerをそれぞれ別の転送Classにすること自体は目的にしない。

## 4. Controller、Presenter、View ModelをEntryの責任へ対応させる

### Controller

Controllerは外部入力を解釈し、Applicationの処理へ接続する。WebではRoute Handlerがこの役割を持ち得る。

```python
def complete_job_handler(request):
    command = CompleteJobCommand(
        actor_id=request.user.id,
        job_id=int(request.path_params["job_id"]),
        reason=request.form["reason"],
    )
    result = execute(command)
    return build_response(result)
```

この関数はControllerであると同時にInbound Adapterである。短く読めるなら、`controller.py`と`request_adapter.py`へ分けない。

### Presenter

PresenterはUseCaseの結果を、画面や外部出力に適した表現へ変換する。HTTP status、Template、表示文言、Link、formatなどが独立して複雑になったなら、Entry配下へ置ける。

```text
entry/
    web/
        complete_job/
            controller.py
            presenter.py
```

UseCaseが単純なResultを返し、Controllerが数行でJSONへ変換できるなら、専用Presenterは不要である。

### View Model

View Modelは、画面表示、操作状態、選択肢、表示文言などに合わせた表現である。Read Modelと同じ型になることもあるが、画面固有の色、Link、権限によるButton状態を持つならEntry側へ分ける理由がある。

```text
entry/
    web/
        job_dashboard/
            view_model.py
            presenter.py
```

境界ごとに同じ項目の型を複製することは目的にしない。意味と変更理由が同じ間は、一つの型がRead ModelとResponse DTOの両方を兼ねてもよい。

## 5. Facade、Orchestrator、Coordinator、Managerを具体名へ戻す

### Facade

Facadeは、複数の内部操作に対して、利用側が使う単純な公開面を提供する。

`data_component/job/__init__.py`がJobの通常利用入口として`complete_job`や`revise_job`を公開し、内部Moduleを利用側に意識させないなら、専用の`facade.py`がなくてもFacadeの役割を持つ。

```python
from .service import complete_job, revise_job

__all__ = ["complete_job", "revise_job"]
```

Python上の深いimportを物理的に不可能にするという意味ではない。通常の入口を示し、内部再編の影響を減らす。

### Orchestrator

Orchestratorは、複数の能力をどの順序と条件で利用するかを決める。FeatureのUseCaseはOrchestratorになり得る。

```text
feature/
    reschedule_job.py
```

複数UseCaseを一つのTransactionへまとめる外側の処理や、長期Processを進めるProcess Managerも、異なる尺度のOrchestrationを行う。何を協調しているかを親概念で示す。

### CoordinatorとManager

Coordinatorは協調する役割を広く表すが、何を協調するかを名前だけでは示しにくい。Managerはさらに意味が広く、状態管理、lifecycle、選択、実行のどれを担当するかが曖昧になりやすい。

`manager.py`や`coordinator.py`を禁止する必要はない。親Packageを含めても責任を説明できない場合は、`connection_pool.py`、`allocation_policy.py`、`job_fulfillment.py`など、管理対象や利用目的を示す名前へ置き換える。

## 6. Policy、Specification、Strategy、Validatorを判断の形で分ける

| 用語 | 中心となる意味 | 代表的な問い |
| --- | --- | --- |
| Policy | 条件を踏まえて何を許可・選択・決定するか | この状況では何を採用するか |
| Specification | 対象が条件を満たすか | この対象は条件に合うか |
| Strategy | 同じ目的を達成する交換可能な方法 | どのAlgorithmで実行するか |
| Validator | 入力や状態が受理可能かを検査する | この値や状態を受け取れるか |

これらの境界は、書籍やFrameworkによって揺れる。名称を厳密な型分類にすることより、判断、条件、実装選択のどれを独立させたのかを説明する。

### 配置例

```text
data_component/
    schedule/
        allocation_policy.py
        assignable_specification.py

feature/
    import_job/
        matching_strategy.py

entry/
    web/
        complete_job.py
```

- `allocation_policy.py`は、稼働条件や優先度から割当方法を決める
- `assignable_specification.py`は、Scheduleが割当可能条件を満たすかを表す
- `matching_strategy.py`は、Import Jobで複数の照合方法を切り替える
- Web入力の必須項目検査はEntryに置ける
- Job状態として成立する条件はData Componentへ置ける

Strategyを実行時に交換する必要がなければ、普通の関数として置ける。PolicyもClassである必要はない。

一つの`if`へPolicy、Specification、Strategyのどれかを必ず割り当てる必要はない。同じ判断が増える、複数の利用側が必要とする、交換可能な方法が存在する、判断自体を業務用語で説明できる、といった事実が現れたときに名前を与える。

## 7. Factory、Builder、Provider、Resolverを生成と選択で分ける

| 用語 | 主な責任 |
| --- | --- |
| Factory | 完成したObjectを生成する |
| Builder | 複数段階の設定や部品からObjectを組み立てる |
| Provider | 必要な値やResourceを利用側へ供給する |
| Resolver | 名前、型、条件、Contextから利用対象を選ぶ |

Factoryは生成規則、Resolverは選択規則を中心にする。Providerは毎回生成することも、既存Resourceを返すこともある。Builderは単純なConstructorで表せない段階的な組立てに意味がある。

### 配置例

```text
data_component/
    job/
        factory.py

external_service/
    mail/
        client_provider.py

feature/
    export_job/
        document_builder.py
        format_resolver.py
```

Jobの作成時に複数の値を導出し、常に守る初期状態があるなら、Job FactoryをData Componentへ置ける。複数のSection、Page、Attachmentを段階的に組み立ててExport文書を作るなら、Document BuilderをFeatureへ置ける。Mail Clientのlifecycleや再利用を管理するなら、Mailの親概念へProviderを置ける。出力形式の選択理由がExport Jobに固有なら、ResolverをFeatureへ置ける。

### `Dependencies.default()`との対応

`Dependencies.default()`は、通常実装を選び、必要なObjectを組み立てる小さなFactoryまたはComposition functionとして働き得る。

```python
@classmethod
def default(cls) -> Self:
    return cls(sender=default_sender)
```

ただし、Connection Poolや長寿命Clientのlifecycleまで必ず持つわけではない。すでに生成された共有Providerを参照する場合もある。

UseCaseが生成済みConnectionを使うだけなら、`ConnectionFactory`を渡す必要はない。UseCase自身がConnection取得時点を決める必要がある場合に、取得能力を直接依存として受け取る。

Constructor一回でObjectが作れるならFactoryは不要である。必須項目を集めてConstructorを呼ぶだけならBuilderも不要になりやすい。実装候補が一つで選択条件もなければResolverを作らず、直接参照できる。

## 8. Mapper、Assembler、Translator、Serializerを変換の意味で置く

- Mapperは、一つの表現と別の表現の対応を扱う
- Assemblerは、複数の値やObjectから公開用のObjectを組み立てる
- Translatorは、異なる言語、Model、Error、Protocolの意味を翻訳する
- Serializer・Deserializerは、Objectと転送・保存形式の相互変換を扱う

これらは排他的ではない。Repository内部の`row_to_job()`はMapperであり、Jobを復元するAssemblerとも説明できる。外部会計SystemのStatusを内部Statusへ変える処理はMapperであると同時にTranslatorでもある。

### 配置例

変換が一つのRepositoryやAdapterだけで使われるなら、そのModule内部に置ける。

```python
# data_component/job/repository.py

def _row_to_job(row: JobRow) -> Job:
    ...
```

外部会計Systemとの語彙差が複数の通信で共有されるなら、外部Systemの親概念へ分けられる。

```text
external_service/
    accounting/
        client.py
        translator.py
        adapter.py
```

一覧画面の表示Objectを複数のRead Modelから組み立てる責任が独立したなら、EntryまたはFeatureの親概念へAssemblerを置ける。

変換を独立させると、外部項目名、欠損値、Enum、Error、version差を、利用目的やDomain Modelへ広げずに済む。一方、型の項目を一対一で数行移すだけなら、利用するAdapterやRepositoryの中に置く方が追跡しやすい。

`mappers/`をトップレベルに作り、無関係な変換を集めない。独立した意味と変更理由があるときにModuleへする。

## 9. Helper、Utility、Common、Sharedを利用範囲だけで決めない

HelperとUtilityは、他の処理を補助する小さな役割を表すが、何についてのコードかまでは示さない。

特定のFeatureだけで使う変換や計算なら、非公開関数またはFeature配下の`helper.py`に置ける。複数箇所から利用されたことだけで、トップレベルの`utils.py`へ移さない。

`common/`と`shared/`も利用範囲を表す名前であり、意味を表す名前ではない。Clock、識別子、Error表現など、複数概念が同じ意味と契約で利用する能力があるなら、その具体名を持つModuleとして置く。

```text
shared/
    clock.py
    identifier.py
```

トップレベルの`shared/`を使う場合は、広い範囲から依存されること、変更影響が広がることを受け入れた判断になる。

Shared Kernelは、複数Bounded ContextがModelの一部を共同所有する関係であり、一般的な共有Utilityフォルダとは異なる。

## 10. Client、Gateway、DAO、Data Mapper、Active RecordをRepositoryと分ける

| 用語 | 中心となる役割 |
| --- | --- |
| Client | 外部ProtocolやSDKを使って通信する |
| Gateway | 外部SystemやResourceへ、Application向けの入口を提供する |
| DAO | Tableや保存データを中心に取得・更新操作を提供する |
| Data Mapper | Domain Objectと保存形式を、Objectに永続化責任を持たせず変換する |
| Active Record | Objectがデータと永続化操作を併せ持つ |
| Repository | Domain上の対象をCollectionのように取得・保存する契約を提供する |

一つのClassが複数の役割を持つことはある。HTTP Clientを使い、外部会計Systemを内部能力として公開するClassはClientとGatewayの両方になり得る。SQLからJob Aggregateを復元するRepository実装はData Mapperの役割も持つ。

### 配置例

```text
external_service/
    accounting/
        client.py
        gateway.py

data_component/
    job/
        repository.py

database/
    audit_log_dao.py
```

- `client.py`は認証、HTTP、Timeout、Provider固有Errorを扱う
- `gateway.py`は会計Systemの能力をApplicationの語彙で公開する
- `data_component/job/repository.py`はJobの復元と保存を扱う
- `audit_log_dao.py`はDomain Objectを復元せず、記録データの追加と検索を扱う

`database/`という親概念は、Database全般の共有能力が独立した意味を持つ場合に置く。JobだけのDAOならJob配下、Auditという概念が成立するならAudit配下も候補になる。

Active Recordは、Objectと保存操作が一緒に変わる小さなApplicationでは単純な選択になり得る。Data MapperやRepositoryが常に優れているわけではない。Domain規則と保存都合を分ける必要、複数保存形式、Test境界などがあるときに分離の利点が増える。

Queryが一つのSQLを実行してRead Modelを返すだけなら、DAO、Gateway、Repositoryを追加せず、Query Moduleから直接利用できる場合もある。

## 11. Projection、Request Model、Response Modelを出力目的で分ける

- Read Modelは、Queryの利用目的に合わせた読み取り表現である
- View Modelは、画面表示、操作状態、選択肢、表示文言に合わせた表現である
- Projectionは、元の状態やEventから導出・保持される読み取り表現である
- Request・Response Modelは、外部Protocolの入力と出力の契約である

同じ型が複数の役割を持つことはある。`JobListItem`をそのままJSONへ返すなら、Read ModelとResponse DTOの両方になり得る。役割が二つあることだけで型を複製しない。

```text
feature/
    list_jobs/
        query.py
        read_model.py

entry/
    web/
        job_dashboard/
            view_model.py
            presenter.py

data_component/
    job_statistics/
        projection.py
```

Eventから非同期に集計値を作り、読み取り用Tableとして保持するならProjectionという独立した意味が生まれる。単にSQLの結果をdataclassへ入れただけで、Projectionと呼ぶ必要はない。

出力目的を分けると、画面変更、API version、読み取り性能、Domain Modelの変更を別々に扱える。代償として、似た型と変換が増える。同じ意味、同じ項目、同じ変更理由が保たれている間は、一つの型を複数境界で利用できる。

## 12. 一つの断面に対応を重ねる

```text
data_component/
    job/
        __init__.py
        domain.py
        repository.py
        service.py

feature/
    complete_job/
        usecase.py
        query.py

entry/
    web/
        complete_job.py

external_service/
    mail/
        adapter.py
```

| ファイル | 主に使う名前 | 同時に成立し得る役割 |
| --- | --- | --- |
| `job/domain.py` | JobのDomain Model | Entity、Value Object、Aggregate Root |
| `job/repository.py` | Job Repository | DAOの一部、Data Mapper、Persistence Adapter |
| `job/service.py` | Jobの公開操作 | Facade、Repository Portの利用側 |
| `complete_job/usecase.py` | Complete Job UseCase | Application Service、Command Handler、Interactor、Orchestrator |
| `complete_job/query.py` | Complete Job Query | Query Handler、Read Model Builder |
| `entry/web/complete_job.py` | Web Entry | Controller、Inbound Adapter、Request Mapper、Presenter |
| `mail/adapter.py` | Mail Adapter | Gateway、Translator、Client wrapper |

この断面で、Interactor、Controller、Facade、Mapperごとに追加ファイルを作る必要はない。役割が独立して複雑になり、別の名前、公開面、Test、変更理由を持つときに初めて分ける。

## 13. 用語を明示するか判断する問い

1. その語は現在のコードの何を区別するか
2. 親となる意味を含めても、一般役割名の方が具体名より説明しやすいか
3. 同じコードに成立する別の役割と、ファイルを分ける必要があるか
4. 専用の型やModuleにすることで、公開面、依存、Testが変わるか
5. 名前だけを付け替える転送層になっていないか
6. 普通の関数、非公開Helper、直接呼び出しで十分ではないか
7. 用語を使わなくても、その用語が区別する責任を構造へ反映できているか

一般的な意味と一致するなら、既存語彙は長い説明を短くできる。一致しないなら、独自定義を加えてまで有名な語を使うより、`complete_job`、`allocation_policy`、`mail_client`のような具体名を使う。

## 14. この章の結論

使われづらい用語の多くは、役割が不要なのではなく、専用の型やファイルにする必要がないため表面に現れにくい。

Featureの`execute()`はUseCase、Command Handler、Interactor、Orchestratorを兼ねられる。Web EntryはController、Inbound Adapter、Presenterを兼ねられる。Repository実装はData MapperとPersistence Adapterを兼ねられる。一つのコードに複数の用語が成立しても、用語ごとに構造を増やさない。

一般役割名は、親となる意味の内部で、その役割が独立して説明できるときに使う。具体名で十分な段階では具体名を使い、区別が実装、公開面、依存、Testとして現れたときに役割名を追加する。
